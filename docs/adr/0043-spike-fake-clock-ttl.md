# 0043. 有効期限は Clock ポートで判定し、偽の時計で時刻の境界をテストする

- 状態: 提案
- 日付: 2026-10-25
- 関連: [design.md](../design.md) 2.7、4.7、4.8、5.3、roadmap M0 のスパイク

## 背景

停止・有効期間・セッションの有効性のキャッシュなど、時刻の境界で振る舞いが変わる処理が多い。実時間を待たずに、境界ちょうどの振る舞いをテストできるかを確かめた。

## 検証（`adapters/ephemeral/memory/memory_test.go`）

- インメモリの EphemeralStore は、期限を `Clock` ポートの現在時刻と比べて判定する（Go のタイマーや `time.Now` を直接使わない）
- 偽の時計（`shared/clock.Fake`）で、TTL 30秒のエントリが「29.999999999秒後には有り、30秒ちょうどで無い」ことを確かめられた
- レートリミット用のカウンタ（固定窓）の窓の切り替わりも、偽の時計で確かめられた

## 決定

- 時刻の取得はすべて `Clock` ポートを通す（design.md 2.7 のとおり）。期限の判定は「`now >= expires_at` なら失効」に統一する（期限の時刻ちょうどで失効）
- EphemeralStore のアダプタは、期限の判定に IAM の `Clock` を使う。Redis のように自前の時計で期限を切るアダプタ（M6）は、TTL を「上限」とみなし、正しさが TTL のぴったりの時刻に依存しない使い方だけをする（5.3 の「反映遅れの上限」はこの前提で成り立つ）
- 時刻の境界の振る舞いのテストは、偽の時計で書く

## 結果

- 停止・有効期間の境界（M2）、キャッシュの反映遅れの上限（M1）のテストを、実時間を待たずに決定的に書ける
- Redis アダプタでは IAM の時計と Redis の時計がずれうる。その分は 5.3 の上限の中に収める

## 検討した代替案

- `time.Now` を直接使い、テストで `time.Sleep` する：遅く、境界ちょうどを狙えず、不安定になる
