# 0045. 内部 ID と外部 ID を分け、採番の方式を差し替えられるようにする

- 状態: 承認
- 日付: 2026-10-25
- 関連: [design.md](../design.md) 2.4、[0039](0039-implementation-basics.md)

## 背景

0039 では ID を UUIDv7 + 型付き接頭辞の1種類とし、同じ値を DB の主キーにも API にも使っていた。

- UUIDv7 は ID から作成時刻が読め、近い時刻に作られた ID どうしの順序も分かる。外部に出すと、ユーザーの登録時期や登録の頻度が漏れる
- OSS なので採番の方式は公開される。内部 ID も、方式が知られていても推測できないものでなければならない
- 採番の方式に弱点が見つかったとき、すぐに差し替えられなければならない

## 決定

### 2種類の ID

| 種類 | 作り方（既定） | 使う場所 |
|---|---|---|
| 内部 ID（`id.New`） | UUIDv7（128bit のうち、時刻の 48bit と版・変種の 6bit を除く 74bit すべてが crypto/rand の乱数。同じミリ秒の中の連番は使わない） | DB の主キーと参照。Storage の外には出さない |
| 外部 ID（`id.NewExternal`） | UUIDv4（122bit が crypto/rand の乱数） | API、Cookie、トークン、ID トークンの `sub`、通知、監査ログ |

- 内部 ID と外部 ID の両方を持つのは、行が多く、ほかの表から多く参照されるもの（users。M3 で orgs）。外部 ID は `public_id` 列に置き、realm 内で一意にする。作成後は変えない
- 外にしか出ない、または行が少ないものは外部 ID だけを持つ（ID そのものを乱数にする）：realm、セッション、通知、サービスアカウントとその API キー、IdP 接続、監査イベント、リクエスト ID、鍵の ID
- 外に出ないものは内部 ID だけを持つ：メール、外部 ID の紐付け（identities）、ロールの付与、データ鍵。M2 でメールなどを API に出すときは外部 ID を足す
- どちらの ID も、方式が公開されていても推測できない（乱数の部分が 74bit 以上）。内部 ID を秘密として扱うわけではないが、外に出さないことで作成時刻も漏らさない

### 採番の方式の差し替え

- ID の文字列の形は `<接頭辞>_<128bit を Crockford Base32 で 26 文字>` に固定し、中身の作り方（UUID の版）は検証しない
- 採番は `id.Generator` の1か所に集める。設定ファイルの `ids.internal` / `ids.external` で選ぶ（`uuidv7` / `random`）。Go ライブラリとして使う場合は `id.SetGenerators` で独自の方式を渡せる
- 外部 ID には、時刻の読める方式（`uuidv7`）を選べない（設定の検証で拒否する）
- 方式を変えても、既存の ID はそのまま有効で、新旧の ID が混在する。マイグレーションは要らない
- 内部 ID の並びが生成時刻の順であることに、コードは頼らない（順序が要る所は時刻の列か、DB の追加順で並べる）
- UUIDv7 は自前で作る。一般的なライブラリ（`github.com/google/uuid` の `NewV7` など）は同じミリ秒の中の順序のために 12bit を連番に使い、乱数が 62bit に減るため

### 確かめ方

- 不変条件のテスト（13.5 に追加）：DB にある内部 ID の値が、公開 API・管理 API の応答、Cookie、通知のペイロード、監査ログの外部出力のどこにも含まれない

## 結果

- 外部から作成時刻や順序を読めない。内部の DB は UUIDv7 のまま、インデックスの効率を保てる
- 方式の弱点が見つかっても、設定の変更だけで新しい ID の作り方を切り替えられる
- users の取得は、API の入口で外部 ID から内部 ID に引き直す1手間が増える
- ID の形から内部 ID か外部 ID かは見分けられない。取り違えは、port の型の項目名（`ID` / `PublicID`）と上記のテストで防ぐ

## 検討した代替案

- すべての ID を乱数にする（1種類のまま）：最も単純だが、行の多い表で主キーの挿入位置がばらつき、B-tree のインデックスの効率が落ちる
- 外部 ID を内部 ID の暗号化で作る（UUIDv7 を鍵付きの置換で隠す）：列は1つで済むが、鍵の管理とローテーションが ID の安定性に直結し、鍵を失うと外部 ID が変わる
- 連番の内部 ID：推測できるうえ、複数インスタンスや DB の移行（`iam storage export / import`）で衝突しやすい
