# 0078. Org 階層は親の付与と org_role を子孫の判定に効かせ、祖先の一覧を書き込み時に計算する

- 状態: 承認
- 日付: 2026-10-27
- 関連: [design.md](../design.md) 3.2、4.5、11.4、[0064](0064-authz-roles-groups-check.md)

## 背景

企業の中の部署やチームを Org で表すと、会社の管理者が部署ごとに所属し直す必要がある。design.md 11.4 は
「親 Org のロールを子に効かせる。祖先一覧は書き込み時に計算する（持ち方はアダプタが決める）。深さに上限。」とする。

## 決定

- フィーチャー `org_hierarchy`（要 `org`）。`orgs.parent_org_id`。SQL のアダプタは閉包テーブル `org_ancestors`
  （`depth` 1 が親）を持ち、親の変更のときに、その Org と子孫の行のうち、その Org より上の祖先を差し替える。
  メモリのアダプタは親をたどる
- 運営者が管理 API の `POST /v1/admin/orgs/{id}:set-parent`（`orgs:update`）で親を設定・外す。`GET /v1/admin/orgs/{id}/children`、
  Org の表示に `parent_id`。個人 Org と削除した Org は扱えない。循環（自分自身・子孫を親にする）は `409 hierarchy_cycle`、
  段数は根を含めて 5 まで（`409 hierarchy_too_deep`）
- 判定（authz/check）：Org の範囲の判定で、その Org の祖先の Org の付与（直接・Group）と org_role の組み込みのロールを、
  祖先の使える所属を持つ間だけ効かせる。判定の Org そのものが使える（削除・停止・有効期間の外・削除の予定でない）ときだけ。
  子の Org の付与は親に効かない
- 子の Org の所属は変えない：Org に入る（ログイン・切り替え）には、その Org の所属が要る。Org の画面の操作（公開 API）も、
  その Org の所属を持つ人が、祖先から効く権限で行う。役割の上下（owner を作れるのは owner など）は、その Org での役割で比べる
- 親の変更で判定の材料のキャッシュを捨てる。Org の削除で、その Org を親から外し、子を根にする
- 監査ログ：`org.parent_set`、`org.parent_cleared`
- フィーチャーを無効にするときは、親子関係を外す

## 理由

- 閉包テーブルなら、判定のたびの祖先の取得が1回の問い合わせになる（判定は書き込みよりずっと多い）
- 子の Org の所属を求めなければ、親の管理者が子の Org に「入れる」ことになり、子の Org のログインポリシーや所属の停止が
  効かなくなる。判定だけを広げれば、入場の条件は子の Org のまま
- 段数の上限で、閉包テーブルの行と、親の変更で書き直す量を抑える

## 影響

- 親の管理者が子の Org を扱うには、子の Org の所属（役割はメンバーでよい）が要る
- Org の owner による公開 API での親の設定は後に回す（両方の Org の権限の扱いを決めてから）

## 検討した代替案

- 祖先を判定のたびに親をたどって求める：判定のたびに段数分の問い合わせ
- 経路（materialized path）を orgs に持つ：子孫の書き直しが文字列の置き換えになり、アダプタごとの差が大きい
- 親の所属で子の Org に入れるようにする：子の Org の入場の条件（ポリシー・停止）を迂回する
