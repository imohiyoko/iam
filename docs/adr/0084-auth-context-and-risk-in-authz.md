# 0084. 認証の文脈とリスクを認可の条件にする

- 状態: 提案
- 日付: 2026-10-28
- 関連: [design.md](../design.md) 2.1、2.8、4.5、4.9、5.3、10、11.8、[0007](0007-auth-warnings.md)、[0064](0064-authz-roles-groups-check.md)、
  [0066](0066-oidc-authorization-code-flow.md)、0069、0074、0077、0078、0081（M6・M7 の PR で追加）

## 背景

今の判定（`authz/check`）の入力は「主体・操作・Org・リソース」だけで、どう認証したか（経路・強さ・経過時間）と、
どれだけ危ういか（リスク）を見ない。認証の警告（0007）と Org のログインポリシー（0069）は入場の条件で、Org に入れるかしか
決めない。「送金は passkey で認証したときだけ」「リスクが高い端末からは閲覧だけ」のような、操作ごとの条件を書けない。

条件を決めたいのは IAM ではなく、IAM を使うマイクロサービス（アプリケーション）と、その上のテナント（Org）である。
決済のサービスは account のリスクに厳しく、閲覧のサービスは緩くてよい。どのリスクを見るか、どのくらいなら何を通すかは、
サービスごと・テナントごとに決められる必要がある。

リスクは1種類ではない。IP の評判、端末、振る舞い、アカウント（漏洩・乗っ取りの兆候）などがあり、提供元も組み込みの
評価器・外部のサービス・連携先自身と分かれる。

## 決定

### 認証の文脈（AuthContext）

判定の問いに、主体の認証の文脈を足す。authz は authn を import しないので、server が組み立てて渡す。

| 項目 | 中身 |
|---|---|
| `amr` | 使った認証手段（`pwd`・`otp`・`hwk`（passkey）・`fed`（外部 ID）など） |
| `factors` | 要素の数 |
| `auth_time` | 認証の時刻（判定の時刻との差が経過時間） |
| `risk` | リスクの種類ごとの点数（0〜100、高いほど危うい）。評価していない種類は無い |
| `attested` | 文脈を IAM が確かめたか（セッションから組み立てたなら真、連携先の申告なら偽） |

- `me:check` と、アクセストークン・セッションに結び付く判定は、セッション（`sid`）から組み立てる（`attested`）
- 管理 API の `authz:check` は、`sid` かアクセストークンを渡せば IAM が組み立てる（`attested`）。主体だけを渡すときは、
  連携先が文脈を申告できる（`attested` でない）。両方あれば IAM の値を使い、申告は捨てる
- 外部 IdP（0077 の Org SSO を含む）でのログインは `fed` に加え、接続の設定 `trust_upstream_amr` が真なら、
  上流の ID トークンの `amr` のうち知っているもの（`hwk`・`otp` など）を `fed:<手段>` として足す。`amr_has(hwk)` は
  `fed:hwk` で満たさない。上流を信じる条件は `amr_has(fed:hwk)` と明示して書く
- サービスアカウント（0074）の文脈は、認証情報の種類（`sak`（API キー）・`client_secret`・`private_key_jwt`）を `amr` に、
  トークンの発行時刻を `auth_time` にする。要素は1。リスクは無い
- 文脈が無い判定（バッチなど）は「何も満たさない」として扱う（fail-closed）。運営者の CLI（`iam` コマンド）は判定を通らないので
  影響しない

### リスク

- リスクは `種類 → 点数（0〜100）` で持つ。種類は組み込み（`ip`・`device`・`account`）と realm で足したもの（`<名前空間>.<名前>`）
- 提供元はリスク評価器（Go インターフェースか Webhook）。点数の尺度を 0〜100 にそろえるのは評価器の責任とする
  （外部サービスの生の値は評価器が変換する）。IAM は尺度を変換しない
- 段階（`low` / `medium` / `high`）は点数の別名として残す。境界は種類ごとに 2.8 の階層で決める（既定は low < 30 ≦ medium < 70 ≦ high）
- 評価のタイミング：
  - ログイン・step-up・Org 切り替え：フック `post_authentication`（0081）の応答に `risk`（種類 → 点数）を足せるようにし、
    評価器はこのフックとして作る。結果はセッションに保存する。フックの失敗はその種類を「評価していない」にする
    （ログインそのものを止めるかは 0081 の `fail_open` に従う）
  - 変化（漏洩の通知・振る舞いの変化など）：管理 API `POST /v1/admin/sessions/{id}:risk` と `POST /v1/admin/users/{id}:risk`
    （ユーザーの全セッション）で評価器や外部のサービスが点数を更新する。権限は `risk:write`。`session.validity_max_delay` の内に判定に効く
  - ホットパス（判定・セッションの検証・イントロスペクション）では評価器を呼ばない
- 評価していない種類を条件が見れば満たさない
- 0007 の警告にも使える（`risk_high.<type>` の警告を出し、入場の条件にもできる）
- 監査ログには点数の変化（`session.risk_updated`）を残す。評価器の根拠（生の値）は残さない

### アプリケーション

条件を決める単位として、アプリケーション（マイクロサービス・リソースサーバー）を登録する。

- アプリケーションは realm に属し、操作の名前空間（`payment` なら `payment:*`）を1つ以上持つ。名前空間は realm で重ならない。
  IAM 自身の操作（`orgs:*`・`members:*` など）は組み込みのアプリケーション `iam` が持つ
- アプリケーションは自分の操作の**要件**（`action → condition`。ワイルドカード `payment:*` 可）と、種類ごとの段階の境界を持つ。
  境界は realm の値を厳しくする方向だけ変えられる
- 呼び出す主体として、OIDC の連携先（0065）かサービスアカウント（0074）を結び付ける。結び付いた主体は、そのアプリケーションの
  要件を変えられ（`applications:manage_requirements`）、イントロスペクション・`authz:check` でそのアプリケーションとして振る舞う
- 管理 API：`/v1/admin/applications`（作成・一覧・取得・削除）、`…/{id}/requirements`。権限は `applications:manage`（realm:owner と realm:admin）

### 条件

条件は次の3か所に書ける。すべて満たして初めて許す（AND）。

1. **付与の条件**（`role_bindings.condition`）：この付与は条件を満たすときだけ効く
   - 例：`org:admin` を「`amr` に `hwk` を含む」ときだけ効かせる
2. **アプリケーションの要件**：その名前空間の操作は、どの付与で許されたかに関係なく条件を求める
   - 例：決済のサービスは `payment:send` に「`auth_time` から 5 分以内」かつ「`account` が 30 未満」を求める
3. **Org の要件**（Org の設定。0062）：テナントがアプリケーションの操作に条件を足す。厳しくする方向だけ（AND で足すので緩められない）
   - Org 階層（0078）がオンなら、判定の Org とその祖先の要件をすべて AND する

同じ操作に複数の要件があれば（`payment:*` と `payment:send` など）すべて AND する。

条件の言語は小さく保つ（任意のスクリプトは入れない）。

```
condition := all(条件...) | any(条件...)
           | amr_has(<手段>...)              # いずれかを使った
           | factors_at_least(<n>)
           | auth_within(<秒>)
           | risk_below(<種類>, <点数>)       # 点数が未満
           | risk_at_most(<種類>, low|medium|high)  # 判定するアプリケーション・Org の境界で段階にして比べる
           | attested()                       # 文脈を IAM が確かめた
```

- アプリケーションの要件と Org の要件は、`attested()` を暗黙に AND する（申告の文脈では満たさない）。付与の条件は書いたとおり
- 評価は判定のキャッシュの外（付与の一覧はこれまでどおりキャッシュし、条件は判定のたびに文脈と突き合わせる）。要件は
  アプリケーション・Org ごとにキャッシュし、変更で捨てる
- 条件は型付きの木で保存し、深さ 4・葉 16 まで

### 判定の結果

- 判定は真偽値ではなく `Decision{Allow, Unmet []string}` を返す。`Unmet` は満たさなかった条件の理由のコード
  （`condition.amr`・`condition.factors`・`condition.auth_age`・`condition.risk.<type>`・`condition.attested`）
- 付与の条件だけで拒んだときは、その付与が条件を満たせば許されたときに限って理由を返す（付与が無い拒否は今までどおり理由なし。
  権限の有無を条件の理由で漏らさない）
- 連携先はこれを見て step-up を促せる（OIDC なら `acr_values`・`max_age` を付けて authorize をやり直す）
- 条件の評価で拒んだ判定は、件数をメトリクスに出す。監査ログには残さない（判定ごとに書くと量が多すぎる）

### 文脈の公開

サービスが自分で判定できるよう、文脈を外にも出す。IAM の判定が基本で、こちらは追加で絞るためのもの。

- イントロスペクションの応答に `amr`・`auth_time`・`risk`（種類 → 点数）を足す（毎回セッションから求める）
- ID トークンには `amr`・`auth_time` を今までどおり載せ、`risk` は載せない（発行の時点の値で古くなるため）

### 権限の引き上げを防ぐ規則（0064）との関係

- 付与・条件・要件を変える操作の権限の検査（`Holds`）は、今の文脈で条件を満たす付与だけを数える
  （条件付きで `org:admin` を持つ人が、条件を満たさないまま条件なしの `org:admin` を付与することはできない）
- 付与の条件を付ける・変える・外すには、その付与を作るのと同じ権限が要る。「緩めるか」は比べない

### 既存の仕組みとの関係

- 重要な操作の直近の認証（`max_auth_age`）は、アプリケーション `iam` の要件 `auth_within` に載せ替える。Org の設定の
  `max_auth_age` は読み替えて残す
- 警告（0007）とログインポリシー（0069）は入場の条件のまま残す（Org に入れるか）。この ADR は入った後の操作ごとの条件
- 設定の階層（2.8）に「アプリケーション」の段を足す：ホスト先 → realm → アプリケーション → Org

## 結果

- サービスごとに、見るリスクの種類と、どのくらいで何を通すかを決められる。テナントはその上に厳しくする方向だけ足せる
- step-up の要否を連携先が理由のコードで判断できる
- リスクの種類を増やしても、判定の作りは変わらない（評価器と種類を足すだけ）
- 判定は文脈を受け取るぶん重くなるが、評価は単純な比較なので、キャッシュに当たったときの目標（1µs）は保てる見込み
- `attested` でない文脈は、付与の条件にしか効かない。要件を確実に効かせたいサービスは `sid` かトークンで判定する
- 点数の尺度をそろえる責任は評価器にある。尺度のずれた評価器を足すと、既存の条件の意味が変わる

## 検討した代替案

- **入場の条件だけで扱う**（警告にリスクを足す）：小さく済むが、Org に入れるか入れないかの2択になり、操作ごとに変えられない
- **realm・Org の設定だけに要件を置く**（アプリケーションを作らない）：サービスごとに見るリスクやしきい値を変えられない
- **文脈を渡すだけで、判定は各サービス**：IAM は小さいが、ポリシーと監査がサービスに散らばる。追加で絞る手段として残す
- **汎用のポリシー言語（CEL・Rego）**：表現力は高いが、判定の性能・監査のしやすさ・権限の引き上げの検査が難しくなる。
  必要になれば条件の言語を置き換えられるよう、条件は型付きの木で保存する
- **リスクを段階だけで持つ**：境界が realm で1つに決まり、サービスごとのしきい値を書けない。点数で持ち、段階は別名にする
- **リスクを提供元の生の点数で持つ**：提供元ごとに尺度が違い、条件が提供元に縛られる。評価器で 0〜100 にそろえる
