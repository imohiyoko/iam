# 0042. SQLite の書き込みトランザクションは BEGIN IMMEDIATE で直列化する

- 状態: 承認
- 日付: 2026-10-25
- 関連: [design.md](../design.md) 2.4、11.14、12、roadmap M0 のスパイク

## 背景

Quota（11.14）では「件数の確認と追加を同じトランザクションで行う」。ほかにも監査ログのハッシュチェーン（直前のハッシュを読んでから追記する）など、読んでから書く処理がある。SQLite で、これを並行に行っても上限を超えたりチェーンが分岐したりしないかを確かめた。

## 検証（`adapters/storage/sqlite/spike_quota_test.go`。modernc.org/sqlite v1.61.0、WAL）

上限5件の表に、64 個の goroutine が同時に「件数を数え、上限未満なら1件追加」を行った（`-race`、3回）。

| トランザクションの開始 | 追加された件数 | `SQLITE_BUSY` で失敗した数 |
|---|---|---|
| `BEGIN IMMEDIATE` + `busy_timeout(10000)` | 常に5 | 0 |
| `BEGIN DEFERRED`（既定） | 5（上限は超えない） | 12〜20 |

DEFERRED でも上限は超えないが、読み取りから書き込みへの昇格の時点で `SQLITE_BUSY` になり、`busy_timeout` も効かないため呼び出し側の再試行が要る。IMMEDIATE なら開始時に書き込みのロックを取るため、`busy_timeout` で順番を待てる。

## 決定

- SQLite アダプタは、すべてのトランザクションを `BEGIN IMMEDIATE`（`_txlock=immediate`）で始め、`busy_timeout` を設定する。WAL を使う
- Storage ポートの約束として「書き込みを含むトランザクションは直列化される（件数の確認と追加を同じ Tx で行ってよい）」を明記した（`shared/port`）。PostgreSQL / MySQL のアダプタでは、同じ約束を行ロックや分離レベルで満たし、契約テストで確かめる
- 契約テスト（`storagetest`）に、並行の一意性（同じ slug の realm、同じユーザーのデータ鍵）と、監査ログの並行の追記でチェーンが分岐しないことを入れた

## 結果

- 単一インスタンスの SQLite で、Quota と監査ログの正しさを保てる
- 読み取りだけのトランザクションも書き込みのロックを取るため、並行の読み取りの性能は落ちる。セッション検証などのホットパスはキャッシュ（5.3）で受け、問題になれば読み取り専用のトランザクションをポートに追加する

## 検討した代替案

- DEFERRED のまま再試行する：すべての呼び出し側に再試行が要り、漏れると稀なエラーになる
- アプリ側のロック（Go の mutex）：複数プロセスから同じ DB を開いた場合に守れない
