# 0063. 監査ログの IP と User-Agent の暗号化

- 状態: 承認
- 日付: 2026-10-26
- 関連: [design.md](../design.md) 6章、9.5、9.6、4.10、[0061](0061-account-deletion.md)

## 背景

監査ログには IP と User-Agent を残す（6.2）。design.md は2つを求める。

- アカウントを削除したら、そのユーザーの個人情報は復号できなくする（4.10、9.5 の crypto-shredding）
- IP は30日の後に IPv4 /24・IPv6 /48 に、User-Agent はブラウザと OS の大分類に切り詰める（9.6）

監査ログは1本のハッシュチェーンで、レコードを後から書き換えられない（書き換えると以降のハッシュが合わなくなる）。
ユーザーのデータ鍵だけで暗号化すると削除の要求は満たせるが、30日の切り詰めは満たせない。

## 決定

- ペイロードの `ip`・`user_agent` には、記録の時点で切り詰めた値（`audit.TruncateIP`、`audit.ClassifyUA`）を平文で置く
- 全文は `client` に暗号化して置く。操作した本人（actor がユーザーのとき）のデータ鍵で暗号化してから、realm と日ごとの鍵
  （`shared_audit_client_keys`、マスター鍵で包む）でもう一度暗号化する。匿名・システムの操作は日ごとの鍵だけ
  - 本人のデータ鍵を消すと（アカウントの削除）、本人の全文は読めなくなる。削除したユーザーの名前の記録には全文を残さない
  - 日ごとの鍵は、その日の終わりから `realm.client_data_retention`（既定30日）の後に Scheduler が消す
    （`audit.client_key.expired`）。その日の全文は誰のものも読めなくなる
  - AEAD の付加データにイベントの ID を含め、暗号文を別のレコードに移しても読めないようにする
- 暗号化は `eventlog.ClientSealer` を通した Storage の中の `Record` が行う（呼び出し側は変えない）。通さない Storage への
  `Record` は切り詰めた値だけを残し、全文は残さない（暗号化を忘れても平文の全文が残らない）
- 外部出力（EventSink）には、これまでどおり IP と User-Agent を含めない（`client` も含めない）
- 調査では `ClientSealer.Open` で全文を読む（読めなければ `ErrClientUnreadable`）

## 理由

- チェーンを書き換えずに、削除と保持期間の両方を「鍵を消す」ことで満たせる。改ざんの検出もそのまま効く
- 切り詰めた値は記録の時点で作るので、保持期間の後も不正のパターン（同じ /24 からの試行など）は追える
- 別の表に IP と UA を出す案は、切り詰めも削除も簡単だが、改ざんの検出の対象外になる

## 影響

- 監査ログのペイロードの `ip`・`user_agent` は切り詰めた値になり、`client` が増える（イベントの形式のバージョンは変えない。
  増えるのは任意の項目）
- 調査用の CLI（全文の復号）は M6 の監査ログの運用でまとめて足す
