# 0089. エンタープライズ向けに全部入りを目指し、以前に除外した機能もフィーチャーとして含める

- 状態: 承認
- 日付: 2026-11-02
- 関連: [design.md](../design.md) 1章、[scope.md](../scope.md)、[roadmap.md](../roadmap.md)、[0005](0005-crypto-no-rsa-pqc.md)、[0010](0010-feature-toggles.md)、
  [0011](0011-build-time-features.md)、[0021](0021-opaque-access-tokens.md)、[0026](0026-first-party-clients.md)、[0031](0031-notifier-ids-only.md)、
  [0066](0066-oidc-authorization-code-flow.md)、[0074](0074-service-accounts.md)

## 背景

M0〜M7 では、速く作るために、用途が当面ないものを範囲から外した。外したのは SCIM、ReBAC、管理画面、サードパーティの連携先、
同意画面、動的クライアント登録、`offline_access`、JWT のアクセストークン、RS256、`profile` などのスコープ、`form_post`、
`request` パラメーター、通知の文面などである。

エンタープライズの導入では、ほかの IAM 製品と同じ範囲を持っていること自体が条件になる。古い SaaS が SAML や RS256 しか扱わない、
調達で SCIM を求められる、といった理由で外せない場面が多い。そこで、何を持つべきかを先に決める必要がある。

## 決定

- 「全部」の範囲を [scope.md](../scope.md) で定める。範囲の決め方は、標準（S）、2 製品以上が持つ機能（P）、調達で求められる項目（C）の和とする。
  scope.md を範囲の正とし、項目を足すときは出どころを書く
- 以前に ADR や design.md で除外したものも、すべてフィーチャーとして含める。除外は速さのためだったので、方針として持たない理由は無い
- 含め方は ADR 0010・0011・0073 の仕組みに従う。新しいフィーチャーは**既定オフ**にし、ビルド時に含めなければバイナリにも入らない。
  全部入りの公式イメージにはすべて含める
- 既定の動作と安全側の選択はそのまま残す。除外をやめたものは、選べるようにするだけにする
  - 署名：既定は ES256 と ML-DSA-65。RS256 は連携先ごとに選べるフィーチャーにし、ホスト先の鍵で RSA を使うときは警告の対象にする（0005 の一部を置き換える）
  - アクセストークン：既定は不透明。JWT（RFC 9068）は連携先ごとに選べるフィーチャーにする（0021 の一部を置き換える）
  - 連携先：サードパーティ、同意画面、動的クライアント登録（RFC 7591・7592）、本人による許可の一覧と取り消しをフィーチャーにする（0026 を置き換える）
  - `offline_access`：フィーチャーにする。ログインの系列から切り離したリフレッシュトークンは、本人が取り消せるようにする（0066 の一部を置き換える）
  - OIDC の `profile`・`address`・`phone`、`claims` パラメーター、`form_post`・`fragment`、JAR、PAR をフィーチャーにする（0066 の一部を置き換える）
  - サービスアカウントのトークンを、自前の API 向け（`aud`・スコープ）に発行し、OIDC のイントロスペクション（`/oauth2/introspect`）で受け付けるフィーチャーを足す。
    発行は今の `POST /v1/admin/token` のまま（ML-DSA の client assertion を扱うため。0074 の理由は残る）。フィーチャーがオフなら、
    イントロスペクションは今までどおりサービスアカウントのトークンを受け付けない（0074 の「影響」の該当の行を置き換える）
  - 通知：既定は ID だけを渡す方式（0031）のまま。文面のテンプレートと SMTP の配送を、別のアダプタとして足す
  - SCIM、ReBAC、管理画面：design.md 1章の「当面やらない」から外し、フィーチャーとして足す
- 順番は roadmap.md の M8〜M12 にし、認証を最優先にする。認証の土台（認証方式のプラグイン 0090）と認証方式の追加を先に作り、
  それから運用と役割ごとのプロセス（0091）、OAuth / OIDC とプロビジョニングの拡張、認可の拡張の順に足す

## 結果

- 調達やほかの製品からの移行で、機能の有無が理由で止まらなくなる
- 範囲が広がる分、v1.0（適合試験、第三者の監査、API の凍結）は遠くなる。v1.0 の対象は、そのときに完成しているフィーチャーに限る
- 攻撃面が増える。既定オフとビルド時の除外を全フィーチャーで守り、XML 署名（SAML）や JWT の検証のような危険な部分は、
  ライブラリの選定（0038 と同じ手順）とファジング（design.md 13 章）を実装の前に決める
- フィーチャーの組み合わせが増える。CI は 0011 のとおり、全部入り・最小構成・最小構成 + 各フィーチャー 1 つずつに絞る

## 検討した代替案

- 必要になったものから足す（M7 のやり方）：エンタープライズの導入では、足りない 1 つで採用が止まり、必要になってからでは間に合わない
- 除外したものは除外のまま、それ以外を全部入りにする：除外の理由が速さだけだったので、残す理由が無い
