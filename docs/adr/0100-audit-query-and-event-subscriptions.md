## 背景

監査ログは Storage にハッシュチェーン（全 realm で 1 本）として残し、外へは EventSink（0071）で 1 つの出力先に流している。
しかし運営者が監査ログを調べるには Storage を直接読むしかなく、改ざんを確かめる手段も CLI の全件検証（`eventlog.Verify`）しかない。
エンタープライズの運用（roadmap M10）では、次のことが求められる。

- 運営者が、期間・種類・主体・対象・Org・結果で監査ログを絞り込み、ページを送って読めること。個人情報の全文（IP・User-Agent。0063）は別の権限に分けること
- Org の管理者が、自分の Org のイベントだけを読めること（他の Org・運営者の情報は見せない。0022・0036）
- 範囲を区切ってチェーンを検証できること
- realm の運営者が、設定ファイルを変えずに、管理 API で Webhook の送り先を登録できること（SIEM を持たない利用者や、複数の送り先が要る場合）
- 監査ログを読んだこと自体が監査ログに残り、大量の読み取りを検知できること

## 決定

### 照会の索引

- 監査ログの行に、ペイロードから導く索引の列（`event_id`・`occurred_unix`・`event_type`・`result`・`actor_type`・`actor_id`・`org_id`）を足す。
  対象の索引は別の表 `shared_audit_refs(seq, ref)` に置く：details のうちキーが `_id` で終わり、値が 1〜200 文字の文字列のものを、重複を除いて入れる
  （`user_id`・`membership_id`・`client_id` など。対象の種類は問わない）。導き方は `audit.IndexOf` の 1 か所に置き、マイグレーションの埋め戻しも同じ規則にする
  （sqlite 00044、postgres 00027。埋め戻しの一致はテストで確かめる）
- 索引の列はハッシュに含めない（チェーンはペイロードだけを守る。0029）。索引の列が書き換えられても他の Org のイベントが漏れないよう、
  照会の結果はペイロードを読み直して `audit.Filter.Matches` で条件を確かめ直し、合わないものを捨てる。ページの大きさは limit + 1 件を読んで決める
- 並びは seq の新しい順。カーソルは seq の 10 進数（不透明な文字列として扱わせる）。limit は既定 50、上限 200。期間は秒の単位で、両端を含む
- 保持期間で切り詰めた範囲（0072）は行ごと消えるので、照会にも 1 件の取得にも出ない。対象の索引も同じ掃除で消す

### 管理 API（運営者）

- `GET /v1/admin/audit-events`：`since`・`until`・`type`・`type_prefix`・`result`・`actor_type`・`actor_id`・`org_id`・`target_id`・`limit`・`after`・`include_client_data`
- `GET /v1/admin/audit-events/{id}`（イベント ID。realm が違えば 404）
- `POST /v1/admin/audit-events:verify`（`from_seq`・`to_seq`。省けば残っている先頭から最新まで）
- 権限は authz の permission で表す（4.11）。`audit:read`（照会・検証）と `audit:read_client_data`（IP・User-Agent の全文の復号）を分ける。
  既定のロールには、`realm:owner` に両方、`realm:security` に両方、`realm:admin` に `audit:read` だけを足す。`realm:support`・`realm:billing` には足さない
- 全文の復号は `include_client_data=true` を付け、`audit:read_client_data` を持つときだけ行う（持たなければ 403。黙って省かない）。
  付けなければ、記録してある切り詰めた IP と User-Agent の大分類だけを返す
- 検証は 1 回で 10 万件まで（超えれば `range_too_large`）。チェーンは全 realm で 1 本なので、既定の realm の運営者だけが使える（ほかの realm では 404）。
  結果は `valid`・確かめた範囲・`anchored`（先頭かチェックポイントに繋がったか）・`prev_hash`・`last_hash`・チェックポイント・最新の seq・壊れた位置と理由。
  範囲を分けて確かめるときは、前の範囲の `last_hash` と次の範囲の `prev_hash` を呼び出し側が突き合わせる。検証の途中で掃除が先頭を消したら 409 を返し、やり直させる
- 検証は CLI の全件の検証と同じ規則で行う（監査の鍵（0086）で鍵付きのレコードを確かめ、鍵付きの後と鍵なしで許す範囲の後の鍵なしのレコードを壊れているとみなす）。
  途中から確かめるときは、直前のレコードが鍵付きかだけを読む。壊れた理由は `seq_gap`・`prev_hash_mismatch`・`hash_mismatch`・`payload_invalid`・
  `realm_mismatch`・`unkeyed_record`・`key_unavailable` のいずれかで、詳細はアプリケーションログにだけ出す

### 公開 API（Org の管理者）

- `GET /v1/me/orgs/{id}/audit-events`。フィーチャー `org_audit_log`（既定オフ、Org に依存）。権限は Org のロールの `org:audit.read`（`owner`・`admin`）
- Org の範囲は、イベントの `org_id`（イベントの項目）がその Org のものに限る。details に Org の ID があるだけのイベント（運営者による停止など）は含めない。
  運営者の停止の理由などを Org に見せないためである。範囲はサーバーが決め、呼び出し側の条件では変えられない
- 返す項目は ID・時刻・種類・結果・主体の種類・リクエスト ID・details。IP・User-Agent・セッション ID・seq・ハッシュは返さない。
  主体の ID は、その Org のメンバー（終了したものを含む）か、その Org のサービスアカウントのときだけ返す。運営者やほかの Org の主体の ID は返さない（0022・0036）

### 照会の監査

- 照会・1 件の取得は `audit.read` を残す（範囲 `realm` か `org`、条件、件数、全文を求めたか、復号した件数）。検証は `audit.verified` を残す（範囲、結果、壊れた位置）
- 読み取りの記録はチェーンに足されるので、読み取りが増えるほど監査ログが増える。大量の読み取りは、この記録をさらに照会するか SIEM で検知する

### イベントの Webhook の購読

- フィーチャー `event_subscriptions`（既定オフ）。管理 API の `/v1/admin/event-subscriptions` で作成・一覧・取得・更新（`PATCH`）・削除（`:delete`）・
  署名の鍵の作り直し（`:rotate-secret`）・テスト送信（`:test`）を行う。権限は `event_subscriptions:manage`（既定では `realm:owner` だけ）
- 購読は realm ごと。1 つの realm に 20 件まで。送るのはその realm の監査ログだけで、種類（完全一致か、`.` で終わる接頭辞。20 個まで。省けば全部）で絞る
- 送り先は https に限る（開発ビルドだけ http 可）。ユーザー情報・フラグメントを含む URL は拒む。IP アドレスで書かれていれば公開のアドレスに限り、
  名前で書かれていれば、送るときに実際につなぐアドレスを確かめる（名前の解決の後で向き先を変えられても通らない）。プロキシは使わず、転送には従わない
- 署名の鍵（`whsec_…`）は作成と作り直しの応答で 1 度だけ返す。Storage には購読ごとのデータ鍵（0063 の DataKeys。owner は購読の ID）で暗号化して置き、
  購読を消せばデータ鍵も消す。署名の形は EventSink の Webhook と同じ（`X-IAM-Signature: t=<秒>,v1=<HMAC-SHA-256("<t>.<本文>")>`）。
  本文は `{"events": [...]}`、購読の ID を `X-IAM-Subscription` に入れる
- 形式は `iam`（0071 の独自 JSON）だけ。個人情報は `omit`（既定）か `pseudonymize` を選ぶ。全文の暗号文は出さない。仮名の鍵は署名の鍵から導くので、
  購読ごとに異なり、鍵を作り直すと仮名も変わる。`raw` と OCSF は持たない（必要なら EventSink を使う）
- 配送は監査ログそのものを outbox にする：購読ごとに配送した位置（`cursor_seq`）を持ち、その先の realm のイベントを読んで送る。作成のときの位置は
  その時点の最新で、過去のイベントは送らない。少なくとも 1 回：送れなければ位置を進めず、10 秒から倍々に待ち（上限 1 時間）、同じイベントをもう一度送る。
  受け取る側はイベント ID で重複を除く。位置は Storage が戻さない（後退する書き込みは無視する）
- 複数のインスタンスで同じ購読を同時に送らないよう、送る前に次の試行の時刻を 1 分先に書いて取る（lease）。lease は厳密な排他ではないので、
  まれに重複して送ることがあるが、少なくとも 1 回の契約の中に収まる
- テスト送信は監査ログに載らないイベント（`event_subscription.test`）を 1 件送り、結果（届いたか、状態コード、失敗の種類）を返す。
  1 つの購読で 1 分に 5 回まで。HTTP はトランザクションの外で行う
- 作成・更新・鍵の作り直し・削除・テスト送信は監査ログに残す。details には送り先のホスト名だけを入れ、パスと鍵は入れない
- 無効にした購読は送らない。有効に戻すと失敗の回数を 0 に戻し、止めていた位置から送り直す
- 配送のループは全 realm で 1 つ。0091 の役割では `worker` に属する

## 結果

- 運営者は管理 API だけで監査ログを調べ、チェーンを確かめられる。Org の管理者は自分の Org の操作の記録を読める
- 個人情報の全文の復号は権限と監査の両方で区切られる
- 設定ファイルを変えずに、realm ごとに複数の Webhook の送り先を持てる。EventSink（全体で 1 つ）はそのまま残る
- 受け入れる制約
  - 索引の列はチェーンで守られない。照会の結果はペイロードで確かめ直すので漏れはしないが、索引が壊されると該当するイベントが見つからないことはある。
    改ざんの有無は検証で確かめる
  - 購読の位置が保持期間より遅れると、その間のイベントは送られずに消える（例えば送り先が保持期間を超えて落ち続けた場合）。送り先の状態（失敗の回数・最後のエラー）は一覧で見える
  - 管理 API の照会と Webhook の本文は、全 realm で共通の seq を返す。seq の飛びから、ほかの realm のイベントの量がおおよそ分かる。
    Webhook の受け取る側は、0071 と違い、`chain.seq` の飛びで抜けを検出できない（ほかの realm と、種類で絞ったイベントの分だけ飛ぶ）
  - 読み取りの記録の分だけ監査ログが増える

## 検討した代替案

- 索引の列をハッシュに含める：チェーンの形が変わり、既存のチェーンの検証と互換が無くなる。ペイロードで確かめ直せば十分である
- 照会の結果をアプリケーションで全件走査して絞る：保持期間 90 日の件数では遅い
- Org の範囲に details の `org_id` も含める：運営者が Org に対して行った操作（停止の理由など）が Org に見える。0022 の開示の規則に合わない
- 購読ごとに別の outbox の表を持つ：イベントを購読の数だけ書き写すことになる。監査ログはすでに順序つきで残っているので、位置だけ持てばよい
- 購読で OCSF・`raw` を選べるようにする：OCSF の変換は EventSink のアダプタにあり、サーバーから import できない（ports and adapters）。
  個人情報をそのまま外へ出す設定を管理 API で変えられるのは危険なので、`raw` は設定ファイルの EventSink に限る
- 署名の鍵をハッシュで持つ：署名には鍵そのものが要る。暗号化して持ち、平文はどこにも残さない
