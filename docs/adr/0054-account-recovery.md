# 0054. アカウントの復旧

- 状態: 承認
- 日付: 2026-10-26
- 関連: [design.md](../design.md) 4.9、4.12、10章、[0050](0050-second-factor.md)、[0051](0051-password.md)、[0053](0053-user-suspension-and-validity.md)

## 背景

M2 で認証手段を失った人が戻れるようにする（4.12）。design.md は経路（リカバリーコード・確認済みメール・Org 管理者と運営者の
復旧リンク）と「復旧専用のセッション」を決めているが、コードの形、セッションの範囲、完了の扱い、パスワードの再設定（0051 で
後回しにしたもの）を決める必要があった。Org 管理者による復旧は Org 管理ユーザー（M7）と一緒に作る。

## 決定

- 経路は `security.recovery.methods`（`recovery_code` / `email` / `operator_link`。既定はすべて）で選ぶ。無効な経路の API は 404。
  メールは realm で `code` の確認を受け入れるときだけ使える
- リカバリーコード
  - 最初の強い認証手段（passkey・TOTP）の登録の応答で10個を1回だけ返す。`/v1/me/recovery-codes:regenerate`（直近の認証が要る）で
    作り直せる。作り直すと古いコードは使えない。運営者の一括の無効化（0052）でも消す
  - 形は Crockford の base32 で16文字（`XXXX-XXXX-XXXX-XXXX`、80 ビット）。先頭4文字は平文の lookup で、照合するハッシュを1つに絞る
    （10個すべてを argon2id で照合しない）。ハッシュはパスワードと同じ argon2id のパラメータ
  - 入力は大文字にし、区切りを除き、O→0、I・L→1 と読み替える
  - 確認済みのメールアドレスとコードで使う。失敗の理由は返さず、アカウントやコードが無いときも同じ重さの照合をする（4.9）
- メールによる復旧：確認済みのアドレスにだけコードとリンクを送り、応答は変えない。フローはログインのフローと別の目的で、取り違えて
  使えない。警告 `recovered_via_email`（既定 warn）を復旧専用のセッションの発行で評価する。deny にすればメールでは復旧できない
- 運営者の復旧用リンク：`POST /v1/admin/users/{id}:recovery_link`（権限 `users:recover`。`realm:owner`・`realm:admin`・`realm:support`）。
  理由は必須。ログイン用のリンクとは封の目的を分け、取り違えて使えない
- 復旧専用のセッション（`restriction: recovery`、`next: recovery`、既定 15 分）
  - 使えるのは passkey・TOTP の登録、パスワードの設定（今のパスワードを求めない）、認証手段の一覧、`/v1/recovery:complete`、
    ログアウトだけ。他の API では未ログインの扱い。外部 ID の連携は戻り先の扱いが別なので含めない
  - 2要素目は求めない（復旧の経路そのものが本人確認）
  - `security_risk` の停止は見ない（4.12：認証手段を入れ替えた後、セキュリティ担当が解除する）。他の停止では理由つきで拒む
- 完了（`/v1/recovery:complete`）：セッションの発行の後に新しい認証手段を登録していなければ `409 new_method_required`。
  完了すると全セッション（このセッションも）を失効させ、リカバリーコードを作り直して1回だけ返し、確認済みの全メールに
  `account_recovered` を通知する。**新しいセッションは出さない**（新しい認証手段でログインし直す）。古い認証手段は残し、
  無効化は本人に勧める
- 0051 の残り：パスワードの再設定はメールによる復旧で行う。パスワードでの新規登録は、メールのコードで登録してから設定する形のまま
  にする（メールの所有の確認を省けないため）
- 後回し：メールによる復旧の待機期間（Org で設定する。M3 以降）、Org 管理者の復旧リンク（M7）

## 結果

- どの経路でも、完了までは他の操作ができず、完了で乗っ取りの途中のセッションも消える
- 復旧の完了は全連絡先に届くので、本人の知らない復旧に気づける
