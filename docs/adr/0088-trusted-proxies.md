# 0088. 信頼できるプロキシを設定で決め、その後ろでは X-Forwarded-For を右から読んで接続元を求める

- 状態: 承認
- 日付: 2026-11-02
- 関連: [design.md](../design.md) 4.1、[0047](0047-m1-login-guards.md)

## 背景

接続元は `RemoteAddr` だけから求めていた（ADR 0047 で後に回した）。リバースプロキシやロードバランサーの後ろに置くと、
全員の接続元がプロキシの IP 1つになる。接続元ごとのレートリミット（`security.login.rate_limit.per_ip`）は同じプロキシを
通る全員で共有され、上限に達すると全員のログインが止まる。監査ログ・セッションの IP・リスクの判定も意味を失う。

## 決定

- `server.trusted_proxies` に、X-Forwarded-For を信じる接続元の IP か CIDR を書く。既定は空で、空なら X-Forwarded-For を読まない
  （直接さらす構成で、利用者が書いた値を信じないため）
- 直接の接続元（`RemoteAddr`）が trusted なら、X-Forwarded-For を右から読み、trusted でない最初のアドレスを接続元にする。
  左の方は利用者が自由に書けるので、一番左は使わない。全部が trusted なら一番左、読めない値に当たったらその右のアドレスで止める
- 複数の X-Forwarded-For ヘッダーは順につなぐ。IPv4 射影の IPv6 は IPv4 にする
- 接続元はレートリミット・監査ログ・セッション・リスクの判定のすべてで同じ値を使う（`withCommon` で1回だけ決める）
- `Forwarded`（RFC 7239）は読まない。主なプロキシは X-Forwarded-For を付けるため

## 結果

- プロキシの後ろでも、接続元ごとの回数が利用者ごとに数えられる。左に偽のアドレスを書き足しても逃れられない
- trusted に含めた範囲から直接つなげる人は X-Forwarded-For で接続元を偽れる。trusted はプロキシの IP だけにする
- 設定を誤ってプロキシを trusted に入れないと、今までどおり接続元はプロキシの IP になる（安全側）

## 検討した代替案

- 一番左の X-Forwarded-For を使う：利用者が書いた値をそのまま信じ、レートリミットを逃れられる
- プロキシの段数（hop 数）で決める：構成の変更で段数が変わると誤った接続元を使う。範囲で書く方が確かめやすい
- `Forwarded` も読む：書式の解析が増え、両方あるときの優先を決める必要がある。需要が出たら足す
