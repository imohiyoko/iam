# 0102. LDAP / Active Directory は外部 ID の connection として扱い、サービスアカウントで探して本人で bind し、同期は止めることだけを自動にする

- 状態: 承認
- 日付: 2026-11-02
- 関連: [design.md](../design.md) 4.1、11.3、11.12、13.2、13.4、[0038](0038-library-selection.md)、[0046](0046-m1-login-flows.md)、
  [0077](0077-org-sso.md)、[0089](0089-enterprise-full-scope.md)、[0098](0098-saml-sp.md)

## 背景

社内のディレクトリ（OpenLDAP、Active Directory）しか持たない組織では、IdP（OIDC・SAML）を立てずに、ディレクトリのパスワードでログインしたい。
また、ディレクトリから人が消えたら iam でもログインできなくし、ディレクトリのグループを iam の Group に写したい。roadmap M9「ディレクトリ」の項目。

LDAP には、次のよく知られた落とし穴がある。

- 空のパスワードの simple bind は「認証しない bind」（RFC 4513 5.1.2）として成功を返すサーバーが多い。成功をログインと取り違えると、誰でも入れる
- 利用者の入力を検索の絞り込みに入れると、`*`・`(`・`)`・`\` で絞り込みを書き換えられる（LDAP インジェクション）
- 平文の LDAP（389）では、bind のパスワードがそのまま流れる
- 名前で探して複数の項目が当たると、どれで bind するかがずれる
- Org の owner がディレクトリの URL を決めると、iam から内部のネットワークにつながる（SSRF）

## 調査結果（2026-11-02 時点。モジュールのソースを確かめた）

| ライブラリ | 確かめたこと |
|---|---|
| go-ldap/ldap/v3 v3.4.15 | Go で広く使われる LDAP のクライアント。`NewConn` と `Start` で自分でつないだ `net.Conn` を使える（SSRF の対策の Dialer をそのまま使える）。`StartTLS`、`EscapeFilter`、`CompileFilter`、`ParseDN`、ページングの制御（RFC 2696）を持つ。`Bind` は既定で空のパスワードを拒む（`AllowEmptyPassword`）。依存は go-asn1-ber v1.5.8 と Azure/go-ntlmssp |

脆弱性データベース（vuln.go.dev・OSV）には、この作業の環境から問い合わせられなかった。CI の govulncheck（design.md 13.4）で確かめる。

## 決定

- LDAP は**外部 ID の connection**として扱う（connections の `type = ldap`、外部 ID は user_identities）。Authenticator のポート（authn_credentials）には載せない。
  ディレクトリは人を作る・名寄せする・Org に入れる側で、OIDC・SAML と同じ扱い（自動の登録、証明済みドメイン、管理ユーザー、`require_sso`）にそろえたいため
  - ログイン・登録・連携は `oauth.LoginFederated`・`LinkFederated` を通る。外部 ID は (connection, 安定した ID)。ID は既定で `entryUUID`、AD では `objectGUID`
    （16 バイトを GUID の文字列にする）。DN と名前は変わりうるので ID に使わない
  - 認証の手段（amr）は `pwd`（ディレクトリのパスワード）。OIDC・SAML の `fed` とは分ける（acr の判定でパスワードと同じ強さ）
  - メールは確認済みとみなすのは、Org 専用の connection（証明済みドメインに限る）と、運営者が `trust_email` にした realm 共通の connection だけ（SAML と同じ）
- ログインの手順
  1. 空のパスワード、制御文字を含む名前、256 バイトを超える名前は、ディレクトリにつなぐ前に断る
  2. 名前ごと（connection と小文字にした名前のハッシュ）の回数の上限（アカウントごとの上限と同じ設定）。ディレクトリのアカウントのロックアウトを iam 経由で起こさせない
  3. サービスアカウントで bind し、`(&{user_filter}({login_attribute}={EscapeFilter(名前)}))` で検索する（件数の上限 2）。ちょうど 1 件でなければ失敗
  4. 見つけた DN で、利用者のパスワードで bind する。失敗は区別せず 401（`authentication_failed`）
  5. AD では `userAccountControl` の無効のビット（0x2）が立っているか読めない項目は失敗にする
  - ディレクトリに届かない、サービスアカウントの bind が通らない、ディレクトリのエラーは 503（`directory_unavailable`）。利用者の誤りと分けて、運営者が気付けるようにする
- 接続
  - `ldaps://`（TLS）か `ldap://` と StartTLS（必須。失敗したら bind しない）。平文の bind・検索はしない。TLS 1.2 以上、ホスト名を確かめる
  - 信頼の起点は `ca_pem`（PEM の証明書）か、無ければシステムのもの。加えて SPKI の SHA-256 のピン（base64、10 個まで）を置ける。ピンは確かめた鎖のどれかに合えばよい
  - サービスアカウントのパスワードは connection の設定に封をして置く（PII の Crypter。目的 `connection.ldap_bind_password`）。API では返さない
  - 1 回の操作の期限は 10 秒。要求のコンテキストが終われば接続を閉じる
  - Org 専用の connection は、つなぐときに実際のアドレスが公開のアドレスかを Dialer で確かめる（ADR 0077 と同じ。開発モードでは許す）
- connection の登録
  - realm：管理 API の `POST /v1/admin/connections:ldap`（`connections:manage`）。サービスアカウントのパスワード・CA・ピン・同期の設定は
    `POST /v1/admin/connections/{id}:update-ldap` で変える。`POST /v1/admin/connections/{id}:sync` で今すぐ同期する
  - Org：`POST /v1/me/orgs/{id}/connections:ldap`（`org:settings`）。OIDC・SAML と同じ上限と個人 Org の禁止。`trust_email` は無い。フィーチャー `org_managed_users` も要る
  - 登録のときに検索の絞り込み・DN・属性名・URL（ldaps か ldap だけ。userinfo・パス・クエリは不可）を確かめる。ディレクトリにはつながない
- 同期（`sync.enabled`）
  - root のインスタンスが 1 分ごとに見回り、時期の来た connection（間隔は既定 1 時間、15 分から 7 日）を同期する。時期とロックは EphemeralStore の `Incr` で決め、
    インスタンスをまたいで 1 回にする。1 回の見回りで 10 個まで
  - 検索はページング（500 件ずつ）、全体で 10 万件まで。読み切れなかったときは、消えた人の扱いとグループのメンバーの外しをしない
  - 紐付いた外部 ID の人がディレクトリに無い・無効なら、`on_missing: suspend`（既定）で利用停止（理由 `customer_request`、外部参照 `ldap:{connection}:…`）にし、
    セッションを終える。戻ってくれば、同期が付けた停止だけを解く。`none` なら何もしない。**消すことは自動にしない**（取り戻せないため。運営者が API で消す）
  - 安全装置：消えた人が 10 人を超え、かつ紐付いた人の 20% を超えたら、その回の停止をやめ、`ldap.sync.completed` に `deprovision_aborted` を残す
    （検索の誤り・ディレクトリの障害で全員を止めない）
  - `sync.provision` なら、まだいない人を登録する（1 回 1000 人まで。登録の規則はログインと同じで、メールが確かめられない人は飛ばす）
  - グループ：`group_base_dn` の下の DN を `memberOf`（`group_attribute`）で読み、Group を作ってメンバーをそろえる（1 回 1000 グループまで、100 件ずつ書く）。
    同期が作った Group だけを `authn_directory_groups` に記録して扱い、同じ名前の既存の Group は取り込まない（`group_conflicts` に数える）。
    Org 専用の connection では、その Org の Group を作り、Org の active なメンバーだけを入れる。変えたら認可のキャッシュを捨てる
  - 監査ログ：`ldap.sync.completed`・`ldap.sync.failed`（件数）、`group.created`、`group.members_synced`
- 新しいテーブル `authn_directory_groups`（connection、ディレクトリのグループのキー、Group）と、外部 ID を connection ごとに引く索引（sqlite 00046、postgres 00029）
- フィーチャー `ldap`（既定オフ）。無効にするときは LDAP の connection を消し、紐付けた外部 ID を無効化し、同期の Group の対応を消す（Group は残す）。
  フィーチャーがオフなら API は 404（`ldap_disabled`）、同期は動かない。ホスト型のログイン画面には出さない（パスワードの画面は後続）。ホームレルム発見には種類 `ldap` で出す
- ファジング：ログインの絞り込みの組み立て（`FuzzLoginFilter`。名前がそのまま 1 つの等しいの条件になること）、ID の文字列化（`FuzzSubject`。違う値が同じ ID にならないこと）、
  グループの DN の解釈（`FuzzGroupOf`）
- テストは同じプロセスの偽物のディレクトリ（`authn/method/ldap/ldaptest`。LDAPS と StartTLS、ページング、空のパスワードの bind を通す本物と同じ振る舞い）

## 結果

- ディレクトリのパスワードでのログインが、OIDC・SAML と同じ外部 ID・登録・Org の規則で動く。ログインの後（セッションの発行、ログインの監査、Org のポリシー）は外部 ID のログインと同じ処理を通る
- iam はユーザーのパスワードを持たない（覚えない）。ディレクトリに届かない間はその connection ではログインできない
- 消えた人は次の同期で止まる（既定 1 時間以内）。すぐ止めたいときは `:sync` を呼ぶ
- ネストしたグループ、AD のプライマリーグループ（`primaryGroupID`）は解かない。`memberOf` を返さないディレクトリ（グループの `member` だけを持つもの）では、グループは同期されない

## 検討した代替案

- Authenticator のポートに載せる（パスワードの一種として）：登録・名寄せ・Org の規則を別に書くことになり、外部 ID の扱い（`require_sso`、連携の解除）とずれる
- 利用者の名前から DN を組み立てて直接 bind する（`uid={name},ou=people,…`）：検索が要らないが、DN の書き換え（エスケープの誤り）と、
  AD の UPN・複数の OU に向かない。サービスアカウントで探して、見つけた DN で bind するのが広く使われる形
- 消えた人を自動で消す：誤った検索・障害で取り戻せない。止めるだけにし、消すのは運営者が決める
- 同じ名前の既存の Group を取り込む：運営者が手で作った Group のメンバーを同期が書き換えてしまう
- 平文の LDAP を設定で許す：閉じたネットワークでも、パスワードがそのまま流れる。許さない
