# 0121. 連携先の権限は登録したカタログの接頭辞の下に置き、IAM 自身の権限と字面で分け、判定は呼び出し元が受け持つカタログに限る

- 状態: 承認
- 日付: 2026-11-07
- 関連: [design.md](../design.md) 4.11、[0064](0064-authz-roles-groups-check.md)、[0084](0084-auth-context-and-risk-in-authz.md)、
  [0109](0109-personal-access-tokens.md)、[0112](0112-par-and-resource-indicators.md)、#195

## 背景

独自のロールの権限には、IAM 自身の管理の権限（`users:delete` など）と、連携先（リソースサーバー）の権限（`doc:read` など）が
同じ `<リソース>:<操作>` の空間で入る。どちらかは、リソースの名前が IAM の組み込みのロールに出てくるか（`role.IAM`）で見分ける。

このため次の問題がある（#195）。

- **IAM との衝突**：連携先が自分の API の権限に `users:delete` を使うと、iam の管理 API の「ユーザーを消す」権限と区別できない
- **後からの衝突**：iam が組み込みの権限を足したとき、その名前を連携先が既に使っていれば、既存の付与が黙って IAM の管理の
  権限に変わる（#196 は、逆向きの漏れで権限の引き上げになった例）
- **連携先どうしの衝突と越境**：権限の名前に持ち主が無いので、2 つの連携先が同じ名前を使える。連携先 A の判定の問い合わせで、
  連携先 B の権限も問い合わせられる
- **一覧が無い**：どんな権限があるかを iam が知らないので、ロールを組む画面で選択肢を出せず、打ち間違いも見つけられない

まだ利用者がいないので、互換のための読み替えや移行の期間は設けず、後に負債を残さない形にする。

## 決定

### 権限の名前の 2 つの空間

- **IAM 自身の権限**：リソースに `.` を含まない（`users:read`・`org:groups.read`）。リソースは組み込みのロールに出てくるものと
  `org` に限る（`role.IAM`）。IAM の組み込みの権限のリソースには `.` を使わない
- **連携先の権限**：`<接頭辞>.<リソース>:<操作>`（`docs.doc:read`・`orders.order:refund`）。接頭辞は登録したカタログ（下）のもの
- どちらでもないもの（`doc:read`、登録していない接頭辞の `x.doc:read`、カタログに無い権限）は使えない

### 権限のカタログ

- 連携先は、realm に **権限のカタログ** を登録する：接頭辞（`^[a-z][a-z0-9-]{0,31}$`、realm の中で一意、作成後は変えられない）、
  表示名、権限の一覧（名前と説明。名前はすべてその接頭辞の下）
- 管理 API `/v1/admin/permission-catalogs`。権限は新しい `permission_catalogs:manage`（realm:owner）
- 独自のロールに入れてよい連携先の権限は、カタログにある権限と、カタログにあるリソースの `*`（`docs.doc:*`）だけ。無ければ
  `400 unknown_permission`
- ロールが使っている権限をカタログから消すこと、ロールが使っているカタログを消すことはできない（`409 catalog_in_use`。
  使っているロールを返す）。黙って効かない付与を残さない

### 判定は呼び出し元が受け持つカタログに限る

- `authz:check` は、カタログの単位で付与する（`resource_type` = `permission_catalog`、`resource_id` = 接頭辞）。連携先の
  サービスアカウントには、自分のカタログの `authz:check` だけを渡す
- 連携先の権限の判定は、呼び出し元がその接頭辞のカタログの `authz:check` を持つときだけ答える（無ければ `403`）。realm 全体の
  `authz:check` は、すべてのカタログと IAM 自身の権限の判定に効く（運営のツール向け）
- バッチの判定は、項目ごとに同じ確かめをする

### 名前の長さ

- 長さは部分ごとに数える：接頭辞 32 文字、リソース 64 文字、操作 64 文字（最長 162 文字）。接頭辞を付けても、連携先がリソースと
  操作に使える長さは減らない
- realm のカタログの数には上限を置かず、1 つのカタログの権限を 500 個までにする

### ほかの入口

- Personal Access Token のスコープ（ADR 0109）と名前空間の要件（ADR 0084）は、権限を狭める・条件を足すだけなので、名前の形
  （2 つの空間）だけを確かめ、カタログは見ない。要件の名前空間 `me` の本人の操作（`me:password` など）は付与の対象ではないので、
  要件のキーとしてだけ使える
- 自前の API のスコープ（ADR 0112）は OAuth のスコープで、権限の名前ではないので変えない
- Org の範囲の独自のロールも同じ（カタログは realm 全体のもので、Org の管理者はそこから選ぶ）

## 結果

- IAM の権限と連携先の権限、連携先どうしの権限が、名前の形と登録で重ならない。iam が組み込みの権限を足しても、連携先の権限の
  意味は変わらない
- 連携先は、自分の権限をカタログとして宣言する必要がある。代わりに、ロールを組む画面で選択肢と説明を出せ、打ち間違いを
  作成のときに拒める
- 連携先のサービスアカウントは、自分のカタログの判定しかできない
- 既存の例・テスト・文書の `doc:read` などは、接頭辞の付いた名前に直す
- 後から足せるもの：`roles:manage` をカタログの単位で渡す（連携先の管理者が自分の権限のロールだけを管理する）、リソース
  （ADR 0112）とカタログの結び付け

## 検討した代替案

1. **接頭辞の形だけを強いる（カタログを持たない）**：IAM との衝突は防げるが、接頭辞に持ち主が無く、連携先どうしの衝突と越境、
   一覧が無いことは残る
2. **IAM の権限を予約の接頭辞（`iam.users:read`）に移す**：IAM の権限をすべて改名し、管理 API・文書を直す必要がある。それでも
   連携先どうしの問題は残る
3. **今のまま（リソースの名前で見分ける）**：どの問題も残る
