# 0114. CIBA は状態を EphemeralStore に置き、本人の承認はプッシュの端末と本人の API で受ける

- 状態: 承認
- 日付: 2026-11-02

## 背景

コールセンター・店頭の端末・別の機器のように、連携先（Consumption Device）の前に本人がいない、またはブラウザで
ログインさせられない場面で、本人の手元の端末（Authentication Device）で承認させたい。標準は OpenID Connect
Client-Initiated Backchannel Authentication Flow - Core 1.0（CIBA）で、エンタープライズの範囲（ADR 0089、[scope.md](../scope.md)）に入っている。

連携先は本人の手がかり（`login_hint` など）を付けて backchannel authentication エンドポイントを呼び、`auth_req_id` を受け取る。
本人の承認の後、連携先は token エンドポイントをポーリングするか（poll）、OP からの通知を受けてから取りに行く（ping）か、
トークンを直接受け取る（push）。

決めることは、(1) zitadel/oidc の `op.Server` との分担、(2) 途中の状態の置き場所、(3) 本人の承認をどの経路で受けるか、
(4) 承認したトークンを何に結び付けるか、(5) 連携先ごとの登録と、受け付ける手がかりの範囲である。

zitadel/oidc（v3.51）は CIBA を持たない。token エンドポイントは知らない `grant_type` を `unsupported_grant_type` で止める。
Device Authorization Grant（ADR 0095）は同じ「要求を預かってポーリングさせる」形で、状態を EphemeralStore に置いている。
プッシュの承認（ADR 0104）は、本人の端末の鍵で署名した承認・拒否を `:callback` で受ける仕組みをすでに持つ。

## 決定

- フィーチャー `ciba`（依存なし、既定でオフ）。オフなら Discovery に出さず、backchannel authentication エンドポイントと
  本人の API は 404、token エンドポイントは CIBA の grant を `unsupported_grant_type` にする。連携先に登録も付けられない
  （`400 invalid_client_metadata`）。管理 API も登録の値を返さない
- 分担：backchannel authentication エンドポイントと、token エンドポイントの `grant_type=urn:openid:params:grant-type:ciba` は
  `op.Server` の前で自前で受ける（他の grant は今までどおり `op.Server`）。連携先の認証は token エンドポイントと同じ手順
  （`client_secret_basic`・`client_secret_post`・`private_key_jwt`）を使う。状態とトークンの発行は `authn/provider`
- 受け付ける連携先：**機密の連携先だけ**（CIBA Core 4。公開クライアントは登録で拒む）。連携先ごとに
  `backchannel_token_delivery_mode`（`poll` か `ping`）を登録したものだけが使える（無ければ `unauthorized_client`）。
  `ping` は `backchannel_client_notification_endpoint`（https、ループバックの http だけ例外）が要る。CIBA だけの連携先は戻り先を持たなくてよい。
  `push` モードは持たない（トークンを連携先へ送り出す口は攻撃面が大きく、poll・ping で足りる）
- エンドポイント（役割は `oidc`）
  - `POST /oauth2/bc-authorize`：`scope`（`openid` が要る。`invalid_scope`）、`login_hint`・`id_token_hint`・`login_hint_token`の
    **ちょうど1つ**（無い・複数は `invalid_request`）、`binding_message`、`client_notification_token`（ping では必須）、
    `requested_expiry`、`acr_values`（フィーチャー `acr` が動いていれば）。署名した要求（`request`）は受けない（`invalid_request`）。
    `user_code` は扱わない（Discovery の `backchannel_user_code_parameter_supported: false`。来ても無視する）。
    応答は `auth_req_id`・`expires_in`・`interval`
  - `POST /oauth2/token`（`grant_type=urn:openid:params:grant-type:ciba`、`auth_req_id`）。ping の連携先もポーリングできる
  - Discovery に `backchannel_authentication_endpoint`、`backchannel_token_delivery_modes_supported`（`poll`・`ping`）、
    `backchannel_user_code_parameter_supported`、`grant_types_supported` の CIBA を足す
- 手がかり
  - `login_hint`：確認済みのメールアドレスか、ユーザーの公開 ID。ログインできる状態のユーザーだけ
  - `id_token_hint`：この realm がこの連携先に発行した ID トークン（署名・`iss`・`aud`/`azp` を確かめ、期限は見ない。
    RP-Initiated Logout と同じ確かめ方。ADR 0094）の `sub`
  - `login_hint_token`：形が連携先と OP の取り決めに依るので受けない（`invalid_request`）
  - 本人が分からない・使えない・手がかりが不正は区別せず `unknown_user_id`（連携先は機密で認証済み。ただし有無の照会に使えないよう、
    連携先ごとと接続元ごとの回数の上限をかける）
- `binding_message`：64 文字まで、制御文字なし（`invalid_binding_message`）。承認の画面・端末にそのまま見せる。監査ログには残さない
- 値と期限：`auth_req_id` は 256 bit の乱数（キーは SHA-256）。期限は `oidc.ciba_ttl`（既定 5 分、10 分まで）で、
  `requested_expiry` はそれより短くするときだけ効く。間隔は `oidc.ciba_poll_interval`（既定 5 秒）
- 状態は EphemeralStore に封をして置く（Crypter。Device Authorization Grant と同じ）
  - 要求（`auth_req_id`）：連携先・本人・スコープ・binding_message・acr・モード・ping のトークン・期限。期限の 2 倍の間残し、
    期限の後のポーリングに `expired_token` を返す
  - 本人の判断：最初の 1 回だけ記録する（`Incr` の印で原子的に決める。プッシュと本人の API が同時に答えても 1 回）。
    ポーリングで `Take` して 1 回だけ答え、要求も消す（その後は `invalid_grant`）
  - 最後のポーリングの時刻と間隔：Device Authorization Grant と同じ `slow_down`（間隔を 5 秒延ばす、1 分まで）を共有の関数で行う
  - 本人の一覧：ユーザーごとに 16 の枠を `Incr` で順に使い、空き（期限切れ・判断済み）を選ぶ。本人の API はこの枠だけを読む
    （EphemeralStore には列挙が無い）。空きが無ければ（本人宛ての未決の要求が 16 件）`429`。これが本人ごとの未決の数の上限になる。
    要求の数そのものは連携先ごと（`ciba:client:`）と接続元ごとに `security.login.rate_limit.per_ip` で数え、プッシュの送信は
    方式のユーザーごとの上限（プッシュ疲れの備え）で数える。連携先ごとの数は既定で 10 分に 100 件なので、
    コールセンターのような大量の利用には `per_ip` を上げる（CIBA 専用の設定は利用者の声を見て足す）
- 本人の承認の経路（Authentication Device）
  - **プッシュ**（フィーチャー `push_auth` が動いていて、本人が端末を登録しているとき）：ADR 0104 の方式に、任意のインターフェース
    `port.BackchannelAuthenticator` を足す。方式は `BeginBackchannel` で、番号の照合の代わりに binding_message と連携先の名前を
    持つチャレンジを全端末に送る（期限は CIBA の要求と同じ。接続元ごとの上限は数えない（接続元は連携先のサーバー）が、
    ユーザーごとの数・拒否が続いたときの停止はそのまま）。端末は `iam-push-v1|context|<チャレンジ ID>|<端末 ID>` に署名して
    `:callback` で中身（連携先の名前・binding_message・スコープ）を取り、承認なら番号 `00` に署名して答える
    （ログインのチャレンジの番号は 10〜99 なので、`00` の承認は番号の違いになる）。応答が届いたら、コアは
    `MethodCallbackResult.Ref` でどのチャレンジかを知り、CIBA の要求に判断を記録する（ping なら通知する）
  - **本人の API**：ログインしたセッションで `GET /v1/me/backchannel-requests`（自分宛ての未決の要求）、
    `POST /v1/me/backchannel-requests/{id}:approve`・`:deny`。ID は要求ごとの乱数の公開 ID で、`auth_req_id` は出さない
  - 端末を登録していない、プッシュの上限を超えた、送信に失敗したときも要求は受け付け、本人の API で承認できる（監査ログに経路を残す）
- トークンを結び付けるもの
  - 本人の API の承認：承認したセッションの系列（`sid`・`auth_time`・`amr`・active な Org）。Device Authorization Grant と同じ
  - プッシュの承認：ブラウザのセッションが無いので、**CIBA 用のセッション**を発行して系列にする（Cookie もトークンも返さない。
    `amr: [swk]`、本人の端末の鍵だけの1要素）。2要素目の確認待ちにはしない（端末の署名がこの認証の要素で、ほかの要素を求める
    経路が無い）が、Org の選択とログインポリシー（`min_aal` など）・警告・フックはログインと同じに効く。本人のセッションの一覧に出て、
    失効させれば CIBA のトークンも止まる。AAL は 1 なので、AAL2 以上を `acr_values` で求めた要求はプッシュでは承認にならない
  - 承認でも、active な Org が使えないセッション・満たせない `acr_values` は拒否として記録する（`access_denied`）
  - トークンは認可コードの交換と同じ `Tokens.Exchange`（不透明なアクセストークン、ID トークン、系列に結び付いたリフレッシュトークン）。
    ID トークンに `nonce` は無い。系列が終わっていれば `invalid_grant`
- ping：判断を記録したら、`backchannel_client_notification_endpoint` に `Authorization: Bearer <client_notification_token>` と
  `{"auth_req_id": …}` を POST する（5 秒で打ち切り、転送を追わない、1 回だけ。届かなくても連携先はポーリングできる）
- ポーリングの答え：知らない・別の連携先の `auth_req_id` は `invalid_grant`、期限切れは `expired_token`、速すぎれば `slow_down`、
  未決は `authorization_pending`、拒否は `access_denied`、承認ならトークン
- 監査ログ：`oidc.ciba_requested`（client_id・スコープ・経路 `push` か `none`）、`oidc.ciba_approved`・`oidc.ciba_denied`
  （client_id・経路 `push` か `self_service`・理由）。トークンの発行は `oidc.authorized`（`grant_type` に CIBA）。
  `auth_req_id`・binding_message・ping のトークンは残さない。プッシュの方式のログ（`method.push.challenge_sent` など）はそのまま
- フィーチャーの無効化：連携先の登録（モードと通知先）を外す（Count / Purge）。途中の要求は EphemeralStore の期限で消える

## 結果

- 状態を EphemeralStore に置くので、複数インスタンスでは共有できる EphemeralStore が要る（`server.multi_instance` の検査で守る）。
  再起動で途中の要求は消え、連携先は `invalid_grant` を受けてやり直す。期限は最長 10 分
- プッシュの方式は、ログイン（番号の照合）と CIBA（binding_message）の2種類のチャレンジを持つ。端末のアプリは `context` で中身を取って
  見せ分ける。プッシュに載せる値（チャレンジ ID・端末 ID・期限）は変えない（0031 の例外の範囲を広げない）
- プッシュの承認だけで、本人の端末の鍵の1要素のトークンが出る。連携先は機密で管理 API で登録したものに限り、本人の端末で
  連携先の名前と binding_message を見て承認するので、CIBA の想定どおりである。AAL2 が要る連携先は `acr_values` で求める
- 本人宛ての未決の要求は 16 件までで、それを超える要求は `429` で止まる（第三者の連携先が本人の枠を埋めうるが、連携先は管理 API で登録した機密のものだけで、期限で空く）

## 検討した代替案

- 状態を Storage の表に置く：本人の一覧は素直に書けるが、短命で1回限りの値のためにポーリングが DB に書き込む。Device Authorization
  Grant（0095）と揃える
- プッシュの承認でも既存のブラウザのセッションの系列を使う：どのセッションに結び付けるかを決められない（本人が承認のときに
  ログインしているとは限らない）
- 系列の無い認可を許す：リフレッシュ・イントロスペクション・ログアウトが系列を前提にしていて、例外が広がる
- push モード：トークンを連携先に送り出すため、送信の失敗と再送・受け手の認証の扱いが増える。poll・ping で足りる
- `login_hint_token` を受ける：形式が取り決めに依り、署名の鍵の配り方も決まっていない
- 番号の照合をそのまま CIBA に使う：連携先の画面に番号を見せる口が CIBA に無い。binding_message がその役になる
