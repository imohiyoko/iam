# 0104. SMS・音声の OTP とプッシュの承認は認証方式のプラグインにし、送信はポートの先のアダプタが行う

## 背景

0089 で、SMS・音声の OTP と、プッシュ通知の承認（番号の照合付き）をエンタープライズの範囲に入れた（[scope.md](../scope.md) 1 章）。
0090・0092 の認証方式のポートは、HOTP のように「クライアントの入力だけで確かめる」方式を前提にしていて、次が足りない。

- 外への送信：SMS・音声はコードを、プッシュはチャレンジを、IAM の外（通信事業者・プッシュの基盤）へ送る。送信は時間がかかり、
  失敗しうる。DB のトランザクションの中で送ると、SQLite では書き込みを止めてしまう
- 送信の回数の制限：SMS は 1 通ごとに費用がかかり、料金の詐取（SMS pumping）・本人への嫌がらせ・総当たりに使われる。
  ユーザー・番号・接続元ごとに数える必要があるが、方式には接続元も、カウンターを置く場所も渡していない
- 別の経路からの応答：プッシュの承認は、ログインしているブラウザではなく、本人の端末から届く。端末からの応答を受ける口と、
  届くまで「待っている」ことをブラウザに返す形が無い。待つ間の問い合わせをユーザーごとの照合の回数（`per_account`）で数えると、
  すぐに使い切る
- 監査ログ：方式は Storage を触らないので、「コードを送った」「端末が拒否した」を記録できない

また、SP 800-63B は公衆電話網（PSTN）の OTP を**制限付きの認証器**（restricted authenticator）とし、使うなら利用者に危険を知らせ、
制限の無い代わりの手段を選べるようにし、使わない選択を組織ができるようにすることを求めている。0031 は、通知に ID だけを渡し、
宛先と秘密を外に出さないと決めている。

## 決定

### 方式

- `authn/method/sms`（方式 `sms`、フィーチャー `sms_otp`）と `authn/method/push`（方式 `push`、フィーチャー `push_auth`）。
  どちらも既定オフ、依存なし、所持の要素、2要素目だけ（`second_factor`）、AAL の上限 2
- 認証情報は 0092 の `authn_credentials` に置く（新しい表は作らない）。電話番号・端末の公開鍵・プッシュの宛先は、ユーザーの
  データ鍵で暗号化したデータに入れる。消去・統合・書き出しと読み込み・フィーチャーの無効化（データを消す）は 0092 のまま効く

### ポートの拡張（0092 への追加）

- `MethodEnv.ClientIP`：要求の接続元（接続元ごとの制限に使う）
- `MethodChallenge.Deliver`：コアが**トランザクションを確定した後**に呼ぶ送信。失敗すればフローを置かず、`503 delivery_failed` を返す
- `MethodChallenge.Events`・`MethodCallbackResult.Events`：方式が残したい監査ログ。コアが種類を `method.<方式>.<出来事>` にして、
  本人の公開 ID と一緒に記録する（方式は Storage を触らない）。詳細に電話番号・宛先・コードを入れない
- `MethodInfo.OutOfBand` と `port.ErrMethodPending`：応答が別の経路（端末）から届く方式。`Complete` が `ErrMethodPending` を返したら、
  コアはフローを回数を数えずに置き直し、`202`（`status: pending`）を返す。クライアントの入力で照合しないので、
  ユーザーごとの照合の回数（`per_account`）では数えない（`/v1/login/` の接続元ごとの制限と応答時間の下限は効く）
- `CallbackAuthenticator`（任意のインターフェース）と `POST /v1/login/methods/{method}:callback`：端末などからの応答を受ける。
  セッションを要さず、本人の確認は方式が行う（プッシュは端末の鍵の署名）。`/v1/login/` の下なので接続元ごとの制限が効く
- `ConfigurableAuthenticator`（任意のインターフェース）：起動時（realm ごと）に `MethodSetup` を受け取って、設定済みの方式を返す。
  `MethodSetup` は、設定ファイルの `methods.<方式>`（文字列の項目。知らない項目は起動を止める）、**方式の名前で前置きした**
  EphemeralStore（コアのキーには届かない。レートリミットと、端末からの応答の受け渡しに使う）、ブラインドインデックス（電話番号を
  平文でキーにしない）、送信のポート（`SMSSender`・`PushSender`）、Clock、開発モードかを持つ。設定や送信のアダプタが足りなければ、
  フィーチャーが動いていても**起動を止める**（fail-closed）

### 送信のポートとアダプタ

- `port.SMSSender`（`Send(ctx, SMSMessage)`。`channel` は `sms` か `voice`）と `port.PushSender`（`Send(ctx, PushMessage)`）。
  設定ファイルの `sms_sender`・`push_sender` で選ぶ（ほかのアダプタと同じ。11.11）
- SMS：`dev`（開発モードだけ。ログに出す）、`twilio`（Twilio の Programmable Messaging と Voice の REST API。音声は TwiML の `<Say>`。
  認証は Account SID と Auth Token か API Key。秘密は環境変数から読んで消す）
- プッシュ：`dev`（開発モードだけ）、`webhook`（運用者のプッシュの中継（FCM・APNs へ送るもの）に、フロー フック・通知と同じ
  HMAC の署名を付けて POST する。https だけ。転送を追わない）
- **0031 の例外として**、SMS の事業者には宛先の番号と本文（コードを含む）を、プッシュの中継には端末の宛先（push token）を渡す。
  届けるのに欠かせない最小限だからである。名前・メールアドレス・ユーザーの ID・接続元は渡さない。SMS の本文は設定の
  テンプレート（`{code}` を必ず含む。既定は英語の 1 文）だけで、IAM が利用者ごとに文面を作らない。プッシュの中身はチャレンジの
  ID・端末の ID・期限だけで、照合する番号は入れない（入れると番号の照合の意味が無い）。運用文書に、事業者が番号とコードを
  受け取ることを書く

### SMS・音声の OTP

- 番号は E.164（`+` と 7〜15 桁）だけを受ける。国番号の許可リスト（`allowed_country_codes`）を置ける（料金の詐取への備え）
- 登録：番号にコードを送り、コードで確かめてから認証情報にする。1 人 3 番号まで。同じ人の同じ番号は `409 credential_limit` と同じく拒否。
  別の人と同じ番号は許す（番号で人を引かず、番号の有無を他人に漏らさない）
- コードは 6 桁（`digits` で 6〜8）を `crypto/rand` で作り、フローの状態には HMAC-SHA-256（フローごとのランダムな鍵）だけを置く
  （状態はコアが封をする）。期限は既定 5 分（`code_ttl`、10 分以下）。比べるのは定数時間で、照合の回数はフローごと
  （`max_attempts`）とユーザーごと（`per_account`）に数える（0092）
- 1 回限り：フローは 0092 のとおり 1 回限り。加えて、ユーザーと番号ごとに最後に送ったコードだけを有効にする（送り直すと前のコードは
  通らない）。使ったら消す
- 送信の制限（窓は `rate_window`、既定 1 時間）：ユーザーごと（`per_user`、既定 5）、番号ごと（`per_number`、既定 5。
  キーは番号のブラインドインデックス）、接続元ごと（`per_ip`、既定 20）、送り直しの間隔（`resend_interval`、既定 30 秒）。
  超えたら `429`
- 経路は `channels`（既定 `sms`）で許したものだけ。`voice` で確かめたときの amr は `tel`、SMS は `sms`
- **制限付きの認証器**：`sms`・`tel` は amr から AAL を求める表（0093）で所持として数える（パスワードと合わせて AAL2）が、
  検証者のなりすましに強くもハードウェアにも結び付かないので AAL3 には届かない。登録の応答に `restricted: true` を返し、クライアントは
  危険と代わりの手段（passkey・TOTP）を示す。表に `Restricted` を足し、`acr.Restricted(amr)` で引ける
  - realm の設定 `disabled_methods` で、realm ごとに方式を止められる（SMS に限らない。止めた方式はその realm で 404）
  - Org のログインポリシーに `deny_restricted_authenticators` を足す。amr に制限付きの手段がある認証では、その Org に入れない
    （理由 `policy.restricted_authenticator`。判定の時と形は 0069 と同じ）

### プッシュの承認

- 端末の登録：`enroll-begin` が 32 バイトのランダムな値を返し、端末は自分で作った鍵の組（ECDSA P-256 か Ed25519。P-256 は
  Secure Enclave・Android Keystore で作れる）の公開鍵（SubjectPublicKeyInfo の DER を base64url）、プッシュの宛先、名前と、
  その値への署名を `enroll-complete` に送る（鍵を持つことの証明）。IAM は端末の ID（`dev_…`、ランダム）を返し、検索キーにする。
  1 人 5 台まで。秘密鍵は端末の外に出ない
- チャレンジ：`begin` が 2 桁の番号（10〜99）とチャレンジの ID を作り、本人の全端末へ送る。番号はブラウザにだけ返し、
  プッシュには入れない。チャレンジは方式の EphemeralStore に、ユーザー・送った端末・番号・期限（`challenge_ttl`、既定 2 分、
  5 分以下）を置く
- 応答：端末は、利用者がブラウザの番号を入れたうえで、`iam-push-v1|respond|<チャレンジ ID>|<端末 ID>|<approve か deny>|<番号>` に
  署名して `:callback` に送る（拒否は番号を入れなくてよく、そのときは `00` に署名する）。IAM は端末の ID で公開鍵を引いて署名を確かめ、チャレンジを**取り出して**（1 回だけ）、本人の・送った
  端末からの応答であることを確かめる。番号が違えば拒否として扱う（推測で通さない）。結果は方式の EphemeralStore に置く
- `complete`：結果がまだ無く期限の前なら `202 pending`、承認なら成功（amr は `swk`）、拒否・番号の違い・期限切れは失敗。
  結果は取り出して 1 回だけ使う
- プッシュ疲れ（MFA fatigue）への備え：番号の照合、ユーザーごとのチャレンジの数（`per_user`、既定 5 / 10 分）と接続元ごとの数、
  拒否が続いたら（`deny_limit`、既定 3 / 30 分）その間はチャレンジを送らない（`429`）。承認・拒否・番号の違いを監査ログに残す
- 端末の宛先は変わるので、端末は `iam-push-v1|token|<端末 ID>|<新しい宛先の SHA-256>|<UNIX 秒>` に署名して `:callback` で変えられる。
  時刻は前回より新しく、今から 5 分以内に限る（古い要求の再送で戻させない）
- 署名する文字列の各項目は、`|` を含まない形（base64url、数、固定の語）に限る。公開鍵の解析は標準の `crypto/x509` で行い、
  P-256 と Ed25519 以外は拒否する。解析と署名の確認にファジングのテストを置く

### 監査ログ

- `credential.registered`（0092）に加えて、`method.sms.code_sent`（`channel`、`credential_id` か登録中）、
  `method.push.challenge_sent`（端末の数）、`method.push.approved`・`method.push.denied`（`reason`：`denied`・`number_mismatch`）、
  `method.push.token_updated`、送信の失敗の `method.delivery_failed`

## 結果

- SMS・音声とプッシュは `authn/method/<name>/`・`features/<name>`・送信のアダプタで足り、Storage アダプタとマイグレーションは変えない
- 方式の拡張点（送信、監査ログ、別経路の応答、設定、方式ごとの EphemeralStore）が増え、メール以外の送信を伴う方式・外部の承認を
  待つ方式（CIBA など）も同じ形で足せる
- SMS の事業者は番号とコードを、プッシュの中継は端末の宛先を受け取る（0031 の例外）。運用者は事業者との契約で扱いを決める
- SMS は制限付きの認証器のまま使える。realm と Org で止められるが、AAL の求め方（0093）は amr のままなので、AAL2 の条件を
  SMS で満たすことは止めない（止めたい Org は `deny_restricted_authenticators` を使う）
- ホスト型のログイン画面にはまだ出さない（0092 と同じ）。端末のアプリは IAM の外で作る

## 検討した代替案

- **SMS も 0031 のとおり通知の ID だけを渡し、外の配信の仕組みが番号とコードを取り出す**：秘密が IAM の外に出る点は同じで、
  配信の仕組みを利用者が作らなければ使えない。事業者のアダプタを直接持つ方が、送信の制限と失敗の扱いを IAM で決められる
- **トランザクションの中で送る**：SQLite では送信の間、書き込みが止まる。送ってから確定に失敗すると、通らないコードが届く
- **プッシュの承認をブラウザの `complete` に端末の署名を貼らせる**：端末とブラウザの間で署名を運ぶ手段が要り、番号の照合を
  端末で行う流れと合わない
- **待つ間の問い合わせもユーザーごとの照合の回数で数える**：既定（10 分に 5 回）ではすぐに使い切る。クライアントの入力を照合しない
  ので、総当たりの備えは要らない
- **プッシュに番号を入れて端末で選ばせる**：番号を見れば押せるので、疲れによる誤承認を防げない
- **電話番号を検索キー（一意）にする**：別の人が同じ番号を持てず、登録の失敗から番号の持ち主の有無が漏れる
