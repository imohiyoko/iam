# 0050. 2段階認証（制限つきのセッション、TOTP、2要素目の passkey）

- 状態: 承認
- 日付: 2026-10-26
- 関連: [design.md](../design.md) 2.8、4.1、4.6、4.9、5.3、13.5、[0049](0049-passkey-details.md)

## 背景

M2 で2段階認証（passkey / TOTP）を作るにあたり、1要素目の後の状態の持ち方、いつ2要素目を求めるか、TOTP の細部を決める必要があった。

## 決定

### いつ求めるか

- 2要素目は passkey と TOTP だけ。メールのコード・マジックリンク・OAuth は2要素目にしない（13.5）
- 2要素目（有効な passkey か TOTP）を登録したユーザーには、設定に関わらず2要素目を求める。本人が足した守りを設定で外さない
- `security.second_factor.required: true` なら、2要素目が未登録のユーザーは、ログインの後に2要素目の登録だけができる
- 本人確認（UV）つきの passkey でのログイン（amr に `hwk` と `user`）は、それだけで2要素とみなし、求めない

### 制限つきのセッション

- 1要素目の後は、通常のセッションの代わりに制限つきのセッション（`restriction` が `second_factor` か `enroll`）を発行する。
  状態を別の仕組み（フローの ID など）に持たず、Cookie・Bearer・入れ替え・失効・検証の遅れの保証（5.3）をセッションと共有する
- 寿命は `security.second_factor.ttl`（既定 10 分）で、通常の寿命より長くならない
- 制限つきのセッションは、決まった API（2要素目の確認、ログアウト。`enroll` ならさらに認証手段の一覧と passkey・TOTP の登録）の他では
  未ログインとして扱う。API ごとの確認に頼らず、セッションを載せる手前で落とす（足した API が既定で守られる）
- LoginResult の `next`（`second_factor` / `enroll`）と `second_factor_methods` で次の手順を返す。Bearer の利用者も同じ
- 2要素目を確かめたら、制限つきのセッションを失効させ、通常のセッションを発行する。amr は1要素目と2要素目を合わせて `mfa` を加え、
  使った認証情報の ID も合わせる（どちらを無効化してもセッションが使えなくなる。4.6）
- `enroll` のセッションで TOTP の登録を完了したら、登録に使ったコードを2要素目として通常のセッションに替える。passkey を登録した
  場合は、続けて2要素目の確認（passkey）をする（登録の応答は MyPasskey のままにする）

### TOTP

- RFC 6238（SHA-1、6桁、30秒）。前後1窓まで受け入れ、使った窓を記録して同じか前の窓のコードを拒否する（再利用の防止）。
  登録の確認に使った窓も記録する
- 秘密は 160bit。PII と同じエンベロープ暗号（ユーザーのデータキー、AAD `totp.secret`）で保存し、削除でクリプトシュレッドされる
- 登録は2段階（開始で秘密と `otpauth://` の URI を返し、コードの確認で保存）。秘密は確認まで EphemeralStore に封をして置く。
  フローの照合は `security.second_factor.max_attempts`（既定 5）回まで
- 1人に1つ（`409 totp_exists`）。作り直すときは無効化してから登録する。無効化は削除せず、ログインの手段に数えないので最後の1つでも外せる
- 照合はユーザーごとにレートリミットする（`security.login.rate_limit.per_account`）。失敗の理由は返さない（4.9）

## 結果

- 2要素目の状態を持つ仕組みがセッションだけになり、入れ替え・失効・期限の扱いを作り直さずに済む
- 新しい API は、制限つきのセッションで使えるものに明示的に足さない限り、制限つきのセッションでは使えない
- ホスト型ログイン画面は TOTP の2要素目だけを扱う。passkey の2要素目と登録（`enroll`）は、利用者のアプリが公開 API で行う（画面を作り込まない。2.5）
