# 0103. X.509 のクライアント証明書（スマートカードを含む）は認証方式のプラグインにし、証明書はコアが mTLS かプロキシのヘッダーから渡す

- 状態: 承認
- 日付: 2026-11-02
- 関連: [design.md](../design.md) 4.1、9.5、11.0、13.2、[0005](0005-crypto-no-rsa-pqc.md)、[0050](0050-second-factor.md)、[0073](0073-build-and-feature-toggle.md)、[0083](0083-multi-realm.md)、
  [0088](0088-trusted-proxies.md)、[0089](0089-enterprise-full-scope.md)、[0090](0090-authenticator-plugins.md)、

## 背景

政府・金融・製造などの企業は、PIV・CAC のようなスマートカードや、端末に入れたクライアント証明書でログインさせることが多い（scope.md の
「X.509 クライアント証明書・スマートカード」。S P C）。0090 で認証方式をプラグインにし、0092 で汎用の認証情報のストアと HTTP を作った。
X.509 をその上に載せるには、次を決める必要がある。

- 証明書はアプリケーションの層（JSON の本文）ではなく TLS のハンドシェイクで届く。iam は平文の HTTP で待ち受け、TLS はプロキシで終えることが多い。
  証明書を誰が受け取り、どう方式に渡すか。利用者が書いたヘッダーを信じない仕組み
- 失効の確認（OCSP・CRL）はネットワークを使う。0092 の方式の呼び出しは Storage のトランザクションの中で、SQLite は書き込みのロックを
  持ったままになる
- 証明書と利用者の結び付け方（証明書そのもの、UPN、メールアドレス、主体の DN）と、その検索キーをブラインドインデックスにすること（0090）
- AAL：スマートカードは SP 800-63B の多要素の暗号デバイスになりうるが、iam はカードの中を確かめられない（0093 の上限の考え方）
- realm ごとに信じる CA が違う（0083）

## 決定

### フィーチャーと方式

- フィーチャー `x509`（依存なし、既定オフ）。方式は `authn/method/x509`、名前は `x509`、所持の要素、1要素目と2要素目に使える
- 方式の設定は設定ファイルの `methods.x509.realms.<realm の slug>`。realm の設定が無ければ、その realm では方式を動かさない（404）。
  設定の誤り（読めない CA、未知の規則など）は起動を止める
  - 仕組みは ADR 0104 の `port.ConfigurableAuthenticator` を使う。`port.MethodSetup` に realm の slug と、`methods.<name>` を
    入れ子のまま読む `Decode`（知らない項目はエラー）を足した。`Setup` が nil を返した方式は、その realm の組に入れない。
    文字列の項目だけの方式（sms・push）は `StringOptions` で読む。コアは中身を知らない
  - OCSP の応答を委ねた署名者が作ったときは、署名者の証明書が `id-kp-OCSPSigning` を持ち、応答を作った時刻に有効であることを
    確かめる（RFC 6960 4.2.2.2。x/crypto/ocsp はこれを確かめない）

### 証明書の受け取り（コア）

- 証明書は2つの経路でだけ受け取り、`MethodEnv.ClientCertificates`（DER の連鎖。先頭が本人）で方式に渡す。連鎖・用途・失効は方式が確かめる
  - **mTLS の専用の待ち受け**（`server.client_certificates.mtls_addr`、`cert_file`・`key_file`）：TLS でクライアントに証明書を求める
    （`RequestClientCert`。TLS の層では連鎖を確かめない。realm ごとのトラストアンカーで方式が確かめる）。証明書を送ったクライアントの
    秘密鍵の所持は TLS の CertificateVerify で確かめてある。待ち受けは認証方式のログイン・2要素目・登録のパス（`/realms/{slug}` の接頭辞を含む）
    だけを通し、それ以外は 404。公開 API の待ち受けで常に証明書を求めると、ブラウザが全部の画面で証明書の選択を出すため分ける
  - **TLS を終えるプロキシのヘッダー**（`server.client_certificates.header`・`header_format`・`proxies`）：直接の接続元（RemoteAddr）が
    `proxies` に含まれる要求でだけ読む。`server.trusted_proxies`（0088）とは別に明示して書かせ、ヘッダーを書いて `proxies` が空なら起動を止める。
    それ以外の接続元からのヘッダーと、mTLS の待ち受けに届いたヘッダーは読まずに消す。形は URL エンコードした PEM（nginx の
    `$ssl_client_escaped_cert`、AWS ALB）か、DER の Base64 のカンマ区切り（Traefik）。連鎖は 8 個、1 つ 16 KiB まで
- ネットワークを使う確かめ（失効）は、コアが Storage のトランザクションの外で呼ぶ `Complete` と `EnrollBegin`（0101）で行う。
  `EnrollComplete`（トランザクションの中）はネットワークを使わず、`EnrollBegin` で確かめた結果（コアが封をして預かる状態）と、
  同じ証明書であることだけを確かめる。始めから完了までの間（フローの期限。既定 10 分）の失効は、失効の結果のキャッシュと同じ程度の遅れとして受け入れる

### 確かめること（方式）

- 連鎖：realm のトラストアンカー（`trust_anchors`）まで。中間 CA はクライアントが送ったものと設定（`intermediates`）を使う。
  期限・名前の制約・署名（SHA-1 を拒む）は Go の `crypto/x509` で確かめる。時刻は Clock
- 本人の証明書：CA でない、鍵用途があれば digitalSignature を含む、鍵は RSA 2048 以上・ECDSA P-256/384/521・Ed25519。
  拡張鍵用途は明示を求める（無い・anyExtendedKeyUsage は拒む）。既定は clientAuth で、`smartcard_logon` や OID も選べる。
  clientAuth だけを受けるときは、連鎖の拡張鍵用途の入れ子も確かめる。RSA は 0005 の対象外（iam が署名するのではなく、
  利用者の CA が発行した鍵を確かめるだけ。PIV・CAC は RSA が多い）
- 失効：`revocation.mode` は `ocsp_crl`（既定。OCSP で分からなければ CRL）・`ocsp`・`crl`・`none`。トラストアンカーを除く連鎖の全部
  （`leaf_only` なら本人だけ）を確かめる
  - OCSP は証明書の AIA か設定の `ocsp_url`。応答の署名（発行者か、委ねられた署名者）、対象の serial、`thisUpdate`・`nextUpdate`
    （ずれは 5 分まで）を確かめる。`golang.org/x/crypto/ocsp` を使う
  - CRL は証明書の配布点と設定の `crl_urls`。発行者の名前と署名が合うものだけを使い、`nextUpdate` の無い・過ぎたものは使わない
  - 結果は `nextUpdate` と `cache_max`（既定 1 時間）の早い方まで、プロセスの中に持つ（数に上限）。取得は 5 秒まで、リダイレクトを
    追わない、大きさに上限（OCSP 64 KiB、CRL 16 MiB）
  - **分からないときは拒む**（fail-closed）。`fail_open: true` なら通すが、失効と分かれば常に拒む
- 利用者との結び付け（`mapping`）：`fingerprint`（既定。証明書の SHA-256）・`san_upn`（SAN の otherName の UPN。1 つだけ）・
  `san_email`（SAN のメール。1 つだけ）・`subject_dn`（主体の DN）。値は規則の名前を前に付けて、汎用の認証情報の検索キー
  （ブラインドインデックス）にする。指紋以外の規則では、同じ値を持つ更新後の証明書でもそのまま入れる。規則を変えたら登録し直す。
  realm の CA は、どれも結び付けの値について同じだけ信じる（分けたいなら realm を分ける）
- フローは始めた証明書の指紋に結び付け、別の証明書では完了できない

### 登録と無効化

- 本人が、ログインしたセッションで mTLS の待ち受け（かプロキシ）から `/v1/me/credentials/x509:enroll-begin`・`:enroll-complete` を呼ぶ。
  開始で連鎖・用途・失効を確かめて何を登録するか（指紋・規則・値・主体・発行者・期限）を返し、完了で同じ証明書なら登録する。
  同じ値が誰かに登録されていれば `409 credential_exists`、1 人 5 個まで（`max_credentials`）。証明書が無ければ `400 client_certificate_required`
- データ（規則・値・指紋・主体・発行者・serial・期限）はユーザーのデータ鍵で暗号化する（9.5）。無効化は 0092 の汎用の無効化
  （本人・運営者・一括）。方式の外に片付けるものは無い（証明書の失効は CA が行う）
- 0092 で後に回した `lookup_key_id` を足す（SQLite 00047、PostgreSQL 00030）。検索キーを作ったインデックス鍵の ID を持ち、
  鍵を切り替えた後も前の鍵で作った検索キーで引ける。前の鍵を鍵の保管から消したら、その鍵で作ったものは登録し直す

### 2要素と AAL

- 同じ認証情報を 2 つの要素に数えない（汎用の変更）：1要素目に使った認証情報は 2要素目の候補に出さず、2要素目に使えば拒む
- amr と AAL（0093。AAL は amr からコアが求める）
  - 既定は `pop`（鍵の置き場所を問わない所持）。単独で AAL1、パスワードなどと合わせても AAL2 まで
  - 本人の証明書を直接発行した CA が `hardware_issuers` にあれば（主体と公開鍵で比べる）、`sc`。0093 の対応表で `sc` を
    「検証者のなりすましに強く、ハードウェアに鍵がある」にした（TLS のクライアント認証はチャネルに結び付く）。単独で AAL1、
    知識の要素と合わせて AAL3
  - さらに `pin_activation: true`（鍵を使うのに PIN が要る、PIV のような多要素の暗号デバイスだと運営者が保証する）なら
    `sc`・`pin`（1要素目なら `mfa` も）。証明書のログインだけで AAL3 になり、2要素目を求めない
  - iam はカードの中を確かめられないので、ハードウェアと PIN は CA についての運営者の宣言に頼る。設定の無い CA の証明書は上がらない
- 方式が宣言する AAL の上限は、ハードウェアの CA を設定した realm で 3、それ以外で 2。Discovery の `acr_values_supported` と
  `acr_values` の受け付けは、上限 3 の方式が動いているときだけ `urn:iam:aal3`・`phrh` を含める

### 監査ログ・無効化・ファジング

- 監査ログは汎用のもの（`login.succeeded`・`login.failed`（`method: x509`、理由に失効や未登録と証明書の指紋）・`credential.registered`・
  `credential.revoked`）
- フィーチャーの無効化は 0092 の汎用の片付け（`x509` の認証情報を消して完了）
- ファジング：SAN の UPN の解析（`FuzzParseSANUPNs`）とプロキシのヘッダーの解析（`FuzzParseCertHeader`）

### この ADR の外

- ホスト型のログイン画面への表示（0092 と同じく、汎用の方式はまだ出さない）。別のホスト名の mTLS の待ち受けからブラウザの
  セッションに戻す流れ
- 運営者による証明書の登録（カードだけの利用者の最初の登録）、確認済みのメールでの自動の結び付け
- OCSP の nonce、デルタ CRL・間接 CRL、証明書のポリシー（OID）での判定、待ち受けのサーバー証明書の再読み込み（今は再起動）

## 結果

- PIV・CAC・社内の CA のクライアント証明書で、ログインと 2要素目ができる。realm ごとに CA と方針を変えられる
- 失効の確認でネットワークを使っても、Storage のトランザクションを長く持たない（0101 の形の上に載る）
- プロキシの後ろでは、ヘッダーを信じる範囲を運営者が明示しなければならない。誤って広く書くと、その範囲から直接つなげる人は
  証明書を偽れる（0088 と同じ）
- 失効が分からないときに拒むので、OCSP・CRL が落ちるとログインできなくなる。キャッシュと `ocsp_crl` で和らげ、`fail_open` は運営者が選ぶ
- AAL3 は CA についての運営者の宣言に頼る

## 検討した代替案

- **TLS の層で連鎖を確かめる**（`RequireAndVerifyClientCert`）：信じる CA を realm ごとに変えられず、失効も確かめられない。拒んだ理由を
  監査ログに残せない
- **公開 API の待ち受けで証明書を求める**：ブラウザが全部の画面で証明書の選択を出し、証明書を持たない利用者を混乱させる
- **`server.trusted_proxies` のプロキシならヘッダーを信じる**：X-Forwarded-For を信じる範囲と、証明書を信じる範囲は同じとは限らない。明示させる
- **登録の完了でも失効を確かめる**：完了はトランザクションの中で、SQLite では書き込みのロックを持ったままネットワークを待つ。
  ポートに、トランザクションの外の確かめを足す案（Preflight）も考えたが、0101 で `EnrollBegin` が外に出たので、そこで確かめれば足りる
- **確認済みのメールで直接ユーザーを引く**：方式に Storage を触らせることになり（0090）、登録の無いまま証明書だけで入れる。
  結び付けは本人の登録（汎用の認証情報）に限り、自動の結び付けは後で決める
- **スマートカードを常に AAL3 にする**：ソフトウェアの鍵の証明書と区別できない。CA ごとの運営者の宣言を要る
