# 0123. JWT のアクセストークン（RFC 9068）は既定オフのフィーチャーにし、トークンの行を残して iam の側の検証と失効は今までどおりにする

- 状態: 承認
- 日付: 2026-11-11
- 関連: [design.md](../design.md) 5.1、5.5、11.0、[0021](0021-opaque-access-tokens.md)、[0089](0089-enterprise-full-scope.md)、
  [0112](0112-par-and-resource-indicators.md)、[0113](0113-sender-constrained-tokens.md)、[0122](0122-rs256-id-tokens.md)

## 背景

ADR 0021 でアクセストークンを不透明にし、リソースサーバーにはイントロスペクションを求めた。API ゲートウェイやクラウドの
マネージドな認可（JWT のオーソライザー）、多くのフレームワークのミドルウェアは、JWKS で JWT の署名を確かめるだけの形を前提にしており、
不透明なトークンでは iam を前に置けない。ADR 0089 は JWT のアクセストークンを連携先ごとに選べるフィーチャーにすると決めた。

## 決定

- フィーチャー `jwt_access_tokens`（既定オフ）。連携先ごとの `jwt_access_tokens: true` で、その連携先のアクセストークンを
  RFC 9068 の JWT にする。既定は不透明のまま
- 形：ヘッダーの `typ` は `at+jwt`、`kid` 付き。アルゴリズムは連携先の `id_token_signed_response_alg`（ES256・ML-DSA-65、
  フィーチャー `rs256` なら RS256）。クレームは `iss`・`sub`・`aud`・`client_id`・`jti`・`iat`・`exp`・`scope`・`auth_time`・
  `sid`、あれば `amr`・`acr`（フィーチャー acr）・`org_id`・`cnf`（DPoP の `jkt`、証明書の `x5t#S256`）。`aud` は自前の API に
  向けた認可（RFC 8707）ならリソースの URI、それ以外は連携先の `client_id`。メールなどの個人情報は載せない
- トークンの行（OIDC のトークン）は今までどおり作り、`jti` を行の ID、行のハッシュを JWT 全体の SHA-256 にする。iam の側
  （UserInfo・イントロスペクション・失効・送信者制約）は `jti` で行を引き、JWT 全体の一致で確かめるので、今までと同じ判定と即時の失効が効く
- リソースサーバーが JWKS だけで確かめる場合、失効・停止・ログアウトは `exp`（`oidc.access_token_ttl`、既定 10 分）まで届かない。
  すぐに止めたい API はイントロスペクションを使う
- Token Exchange で出すトークンは不透明のまま（`act` の扱いは別に決める）
- フィーチャーが止まっていれば JWT の形のアクセストークンはどこでも受けない（fail-closed）。無効化は連携先の設定を外して完了する

## 結果

- API ゲートウェイ・JWT のオーソライザーなど、イントロスペクションを呼べないリソースサーバーの前に iam を置ける
- JWT だけで確かめるリソースサーバーでは、失効が期限まで遅れる（ADR 0021 の理由）。既定オフと連携先ごとの選択で範囲を限る
- ML-DSA-65 を選ぶとトークンが 4KB を超える。ヘッダーの大きさの制限のある経路では ES256 か RS256 を選ぶ

## 検討した代替案

- 行を作らずに JWT だけにする：失効・UserInfo・送信者制約・イントロスペクションをすべて作り直すことになり、即時の失効も失う
- アクセストークンの署名に専用のアルゴリズムの設定を足す：連携先の ID トークンと同じ鍵で足りる。必要になれば足せる
- realm の既定を JWT にする設定：既定を安全側に保つ方針（ADR 0089）に反する
