# 0067. 認証の文脈とリスクを認可の条件にする

- 状態: 承認
- 日付: 2026-10-28
- 関連: [design.md](../design.md) 2.1、4.9、5.3、10、11.8、[0007](0007-auth-warnings.md)、[0064](0064-authz-roles-groups-check.md)

## 背景

今の判定（`authz/check`）の入力は「主体・操作・Org・リソース」だけで、どう認証したか（経路・強さ・経過時間）と、
どれだけ危ういか（リスク）を見ない。認証の警告（0007）と Org のログインポリシー（4.4）は入場の条件で、Org に入れるかしか
決めない。「送金は passkey で認証したときだけ」「リスクが高い端末からは閲覧だけ」のような、操作ごとの条件を書けない。

リスクは1種類ではない。IP の評判、端末、振る舞い、アカウント（漏洩・乗っ取りの兆候）などがあり、提供元も組み込みの
評価器・外部のサービス・連携先自身と分かれる。

## 決定

### 認証の文脈（AuthContext）

判定の問いに、主体の認証の文脈を足す。authz は authn を import しないので、server が組み立てて渡す。

| 項目 | 中身 |
|---|---|
| `amr` | 使った認証手段（`pwd`・`otp`・`hwk`（passkey）・`fed`（外部 ID）など） |
| `factors` | 要素の数 |
| `auth_time` | 認証の時刻（判定の時刻との差が経過時間） |
| `risk` | リスクの種類ごとの段階（`low` / `medium` / `high`）。評価していない種類は無い |

- `me:check` と、アクセストークン・セッションに結び付く判定は、セッション（`sid`）から組み立てる
- 管理 API の `authz:check`（連携先が主体を指定する）は、連携先が文脈を渡す。渡された値は連携先の申告として扱い、
  IAM が持つ値（セッションを指定したときのそれ）があればそちらを優先する
- 文脈が無い判定（バッチなど）は「何も満たさない」として扱う（fail-closed）

### リスク

- リスクは `種類 → 段階` の組で持つ。種類は組み込み（`ip`・`device`・`account`）と realm で足したもの（`<名前空間>.<名前>`）
- 提供元はリスク評価器（Go インターフェースか Webhook。11.8 のフックと同じ作り）。点数を返してもよいが、IAM には
  種類ごとのしきい値で段階にして持つ（しきい値は 2.8 の階層で設定し、Org は厳しくする方向のみ）
- 評価のタイミングはログイン・step-up・Org 切り替え（セッションに保存）と、評価器が出す変化のイベント（再評価してセッションを
  更新し、`session.validity_max_delay` の内に判定に効く）。ホットパスで評価器を呼ばない
- 評価器が失敗・時間切れなら、その種類は「評価していない」になる（条件に `risk.<type>` があれば満たさない）
- 0007 の警告にも使える（`risk_high.<type>` の警告を出し、入場の条件にもできる）

### 条件

条件は次の2か所に書ける。どちらも満たして初めて許す（AND）。

1. **付与の条件**（`role_bindings.condition`）：この付与は条件を満たすときだけ効く
   - 例：`org:admin` を「`amr` に `hwk` を含む」ときだけ効かせる
2. **操作の要件**（realm・Org の設定。`action → condition`）：この操作は、どの付与で許されたかに関係なく条件を求める
   - 例：`payment:send` は「`auth_time` から 5 分以内」かつ「`risk.account` が `low`」

条件の言語は小さく保つ（任意のスクリプトは入れない）。

```
condition := all(条件...) | any(条件...)
           | amr_has(<手段>...)          # いずれかを使った
           | factors_at_least(<n>)
           | auth_within(<秒>)
           | risk_at_most(<種類>, low|medium|high)
```

- 評価は判定のキャッシュの外（付与の一覧はこれまでどおりキャッシュし、条件は判定のたびに文脈と突き合わせる）
- 条件を満たさずに拒んだときは、応答に理由を添える（`condition.amr`・`condition.auth_age`・`condition.risk.<type>` など）。
  連携先はこれを見て step-up を促せる。リスクの根拠（評価器の生の値）は出さない
- 条件の変更は監査ログに残す（`role.binding_*`・`authz.requirement_*`）。権限の引き上げを防ぐ規則（0064）は条件付きの付与にも
  そのまま効く（条件を外す・緩めるのは付与と同じ権限が要る）

### 既存の仕組みとの関係

- 重要な操作の直近の認証（`max_auth_age`）は、IAM 自身の操作の要件として同じ仕組みに載せ替える
- 警告（0007）とログインポリシー（4.4）は入場の条件のまま残す（Org に入れるか）。この ADR は入った後の操作ごとの条件

## 結果

- 操作ごとに「どう認証したか」「どれだけ危ういか」で許可を変えられる。step-up の要否を連携先が理由のコードで判断できる
- リスクの種類を増やしても、判定の作りは変わらない（評価器と種類を足すだけ）
- 判定は文脈を受け取るぶん重くなるが、評価は単純な比較なので、キャッシュに当たったときの目標（1µs）は保てる見込み
- 連携先が渡す文脈は申告なので、IAM のセッションに結び付かない判定では、条件は連携先の自己申告を信じることになる

## 検討した代替案

- **入場の条件だけで扱う**（警告にリスクを足す）：小さく済むが、Org に入れるか入れないかの2択になり、操作ごとに変えられない
- **汎用のポリシー言語（CEL・Rego）**：表現力は高いが、判定の性能・監査のしやすさ・権限の引き上げの検査が難しくなる。
  必要になれば条件の言語を置き換えられるよう、条件は型付きの木で保存する
- **リスクを点数のまま比べる**：提供元ごとに尺度が違い、条件が提供元に縛られる。段階にそろえる
