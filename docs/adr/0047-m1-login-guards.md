# 0047. M1 のログインの守り（警告、応答時間の下限、レートリミット）の細部

- 状態: 承認
- 日付: 2026-10-25
- 関連: [design.md](../design.md) 4.1、4.9、10章、11.0、11.12、[0007](0007-auth-warnings.md)、[0011](0011-build-time-features.md)

## 背景

M1 で認証の警告、本人確認の前の応答時間の統一、インメモリのレートリミットを作るにあたり、design.md に書かれていない細部を決める必要があった。

## 決定

### 警告（10章）

- 評価はセッションの発行（`session.Manager.Issue`）の中、セッションを作る前に1か所で行う。経路は Evidence（`amr`、OAuth のメール確認状況）を渡すだけで、ルールを知らない
- `single_factor` は `amr` を RFC 8176 の要素の種類（知識・所持・生体）に分け、2種類未満なら該当とする。`mfa` があれば該当しない。`fed` はプロバイダ側の要素数が分からないため1要素とみなす
- `oauth_email_unverified` は、紐付け済みの外部 ID でのログインで、プロバイダがメールを確認済みとしなかったときに該当する（未確認のメールでは登録できないため、登録時には出ない）
- アクションは `security.warnings`（コード → `ignore` / `warn` / `deny`）で変える。未知のコードやアクションは起動時に拒否する
- `warn` と `deny` の警告は `sessions.warnings` と監査ログ（`session.created` の details）に残し、ログインの応答の `warnings` で本人に返す。`ignore` は残さない
- `deny` はトランザクションごと戻す（登録も行わない）。本人確認の後なので `403` で `warning_denied.<code>` を返し、該当したすべてを `reasons` に入れる（4.9）
- フィーチャー `warnings` が動いていなければ評価器を通さない（11.0）

### 空の DB でのフィーチャーの有効化（11.12 の例外）

- 台帳も realm も無い DB で起動したとき、設定で有効（省略時は既定でオン）のフィーチャーを台帳に `active` で記録し、監査ログに `feature.enabled`（`reason: fresh_install`）を残す
- 片付けるデータも準備するデータも無いため、enable → enabling → active の手順を省いても保証は崩れない
- 既存の DB には行わない。新しく含めたフィーチャーは、これまでどおり `iam features enable` で明示的に進める（それまでは起動時に警告）

### 応答時間の下限（4.9）

- `POST /v1/login/...` の応答を手元に溜め、受けてから `security.login.min_response_time`（既定 300ms）が経つまで送らない。失敗も成功も、レートリミットの応答も同じ
- 下限は処理時間の差を隠すためのもので、下限を超えた処理（プロバイダへの問い合わせなど）は延ばさない。アカウントの有無で処理の内容を変えないこと（通知も両方で送る）と組み合わせる

### レートリミット（4.1）

- EphemeralStore の `Incr` による固定窓。`security.login.rate_limit`（既定：10分ごとに接続元 100 回、アドレス 5 回）
- 接続元ごと：`/v1/login/...` の POST を数える。IPv6 は利用者が /64 を自由に使えるため /64 でまとめる
- 接続元は `RemoteAddr` から求める。信頼できるプロキシの扱い（X-Forwarded-For）は M6 で足すため、それまでリバースプロキシの後ろに置くと、接続元ごとの回数はプロキシの IP 1つで数えられる。上限に達すると、同じプロキシを通る全員のログインが窓の終わりまで `429 rate_limited` になる。M1 でプロキシの後ろに置くなら `security.login.rate_limit.per_ip` を利用者の数に合わせて上げる（アドレスごとの上限はプロキシに関係なく効く）
- アドレスごと：メールのフローの開始を数える。キーはブラインドインデックスにし、アドレスを EphemeralStore に置かない。登録の有無に関係なく数えるので、制限されたことからアカウントの有無は分からない
- 超えると `429 rate_limited` と `Retry-After` を返す。監査ログの `rate_limit.triggered` は窓ごとに最初の1回だけ残す（攻撃中に監査ログを溢れさせない）

## 結果

- 警告の追加は、ルールを1つ足すだけで全経路に効く
- 空の DB では設定どおりに起動でき、既存の DB では構成変更の手順が保たれる
- 固定窓は窓の境目で最大2倍まで通る。M1 ではこれを受け入れ、必要になればスライディング窓に替える

## 検討した代替案

- 応答時間を揃えるのに乱数の待ちを足す：平均を取れば差が見えるため、下限で揃える
- 警告の評価を経路ごとに書く：経路が増えるたびに漏れが出やすい（0007 の「経路を知らないルール群」に反する）
- フィーチャーの有効化を M1 でも必ず CLI で行う：`iam features enable` は後のマイルストーンのため、M1 では既定でオンのはずの警告が動かなくなる
