# 0086. 監査ログのハッシュチェーンは KeyStore の監査の鍵で HMAC にし、鍵なしに戻ることを改ざんとみなす

- 状態: 承認
- 日付: 2026-10-31
- 関連: [design.md](../design.md) 6.3・6.5・9.5、[0029](0029-audit-retention.md)、[0072](0072-retention.md)

## 背景

Storage の監査ログは SHA-256(前のハッシュ || ペイロード) のチェーンで、書き換えると後ろのハッシュが合わなくなる。
ただし鍵が無いので、DB に書き込める人（DB の権限の漏洩、バックアップからの書き戻し）は、書き換えた後のハッシュを
全部計算し直せる。SIEM に送ったチェーンの位置（`chain.seq`・`chain.hash`）と突き合わせれば分かるが、
SIEM を使わない構成（標準出力だけ）では `storage import` や検証のコマンドで見つけられない。

## 決定

- KeyStore に監査の鍵（`audit_keys` と `current_audit_key`。32 バイト、ID は `ak_…`）を置ける。ポートは `port.AuditKeyStore`
  （KeyStore の任意の追加）。マスター鍵・インデックス鍵とは別の鍵で、ID も重ねない
- 監査の鍵があれば、新しいレコードのハッシュを HMAC-SHA-256(監査の鍵, 前のハッシュ || ペイロード) にし、レコードに鍵の ID
  （`key_id`）を残す。鍵が無い構成と、鍵を置く前のレコードは今までどおり SHA-256（`key_id` は空）
- 検証は `key_id` の鍵で確かめる。鍵付きのレコードの後に鍵なしのレコードが来たら壊れているとみなす（鍵の無い人が後ろを
  鍵なしで作り直すことを防ぐ）。切り詰めのチェックポイントにも最後に消したレコードの `key_id` を残し、その後ろも同じ規則にする
- 鍵付きの範囲は DB の外（KeyStore）で決める。監査の鍵を置いていれば、`audit_unkeyed_until`（既定 0）より後の seq は
  鍵付きでなければ壊れているとみなす。DB の中の印（最初の鍵付きのレコード）だけでは、最初の鍵付きのレコードから後ろを丸ごと
  鍵なしで作り直されると見分けられないため。鍵を置く前からの監査ログがある構成だけ、その最後の seq を書く
- 監査の鍵があれば、起動して最初に書くレコード（新しい DB のフィーチャーの記録）から鍵付きにする
- 鍵を入れ替えたら、新しいレコードから新しい鍵を使う。古い鍵は監査ログの保持期間が過ぎるまで消さない（検証に要る）
- `iam keys generate` で作る鍵の組には監査の鍵も入れる（新しい構成は最初から鍵付きで、`audit_unkeyed_until` は要らない）。
  前からの構成は鍵を足した時点から鍵付きで、`audit_unkeyed_until` に鍵を足す前の最後の seq を書く
- `iam storage import` は設定の KeyStore の監査の鍵で検証する

## 結果

- DB だけを書き換えられる人は、鍵付きのレコードを作り直せない。鍵なしに戻すこと（鍵付きの範囲を丸ごと作り直すことも）・
  途中を消すことも検出できる
- 鍵付きにする前のレコード（鍵なし）は、今までどおり SIEM との突き合わせで守る
- 監査の鍵は検証にだけ要る。失うと、その鍵で作ったレコードを確かめられない（記録そのものは読める）
- 前からの構成は、鍵を足した後に `audit_unkeyed_until` を書くまで検証が通らない（エラーが鍵なしのレコードの seq を示す）

## 検討した代替案

- マスター鍵やインデックス鍵から導く：入れ替えの後に古い鍵を消すと、保持期間の中の監査ログを確かめられなくなる。消してよい時期が鍵ごとに違う
- 既存のレコードを鍵付きで計算し直す：SIEM に送ったチェーンの位置と合わなくなり、今までの記録の証拠を失う
- 鍵付きの範囲を DB の中の印（最初の鍵付きのレコード、チェックポイントの `key_id`）だけで決める：DB を書き換えられる人が
  印ごと鍵なしで作り直せる
- 電子署名（Ed25519 など）：公開鍵だけで第三者が検証できるが、署名の鍵の管理が増える。今は運営者が自分で確かめられればよい
