# 0120. イントロスペクションに主体の種類と認証の方式を載せ、API キーの検証とリソースを確かめてよい連携先の限定はどちらも既定オフで足す

- 状態: 承認
- 日付: 2026-11-07
- 関連: [design.md](../design.md) 5.10、11.0、[0021](0021-opaque-access-tokens.md)、[0073](0073-build-and-feature-toggle.md)、
  [0074](0074-service-accounts.md)、[0109](0109-personal-access-tokens.md)、[0112](0112-par-and-resource-indicators.md)

## 背景

自前の API（リソースサーバー）を iam に任せるホスト先（imohiyoko/API など）から、次の 2 つの要望が来た（#151・#154）。

- リソースサーバーが、サービスアカウントの認証情報（`sat_…` と API キー）をイントロスペクションで確かめ、主体の種類・公開 ID・
  所属の Org・認証の方式を受け取りたい
- 呼び出したリソースサーバーと `aud` が違うトークンは、iam が `active: false` で返してほしい

ADR 0112 で、リソースに向けた `sat_…` のイントロスペクション（`sub`・`aud`・`scope`・`org_id`）と、`aud` の確認をリソースサーバーに
任せることはもう決めている。残るのは、(1) 主体の種類と認証の方式を応答に載せること、(2) API キーをイントロスペクションで受けるか、
(3) iam の側でも呼び出し元とリソースを結ぶか、である。

iam は OSS として多くの機能を持ち、使わない機能は簡単に外せることを方針にする（ADR 0073）。(2) と (3) は、要らないホスト先には
安全側の今の動きのままにしたい。

## 決定

### 応答に主体の種類と認証の方式を載せる（常に）

- 使えるトークンのイントロスペクションに `principal_type`（`user` か `service_account`）を足す。RFC 7662 2.2 の拡張の項目
- サービスアカウントのトークンには `amr`（発行に使った認証の方式：`client_secret`・`private_key_jwt`・`workload_identity`、
  API キーは `sak`）と `auth_time`（発行の時刻、API キーは確かめた時刻）を載せる
- 新しい力は足さない（今までも判定に使っている値を見せるだけ）ので、フィーチャーにしない

### API キーのイントロスペクション（フィーチャー `api_key_introspection`、既定オフ）

- 依存は `service_accounts`。登録は `features/apikeyintrospection`。持つデータは無い
- 動いているときだけ、`/oauth2/introspect` で API キー（`sac_….<秘密>`）を受け、`active: true`・`token_type: api_key`・
  `sub`・`principal_type: service_account`・`org_id`・`amr: ["sak"]`・`auth_time`・`iss`、期限があれば `exp` を返す。`aud` と
  `scope` は無い（API キーは向け先を持たない）
- 止まっていれば API キーは今までどおり `active: false`
- 停止・削除・有効期間・認証情報の無効化・Org の状態は、管理 API の Bearer と同じ確かめ（`usable`）で毎回効く
- 秘密はログにも監査にも出さない（イントロスペクションはトークンを記録しない）

### リソースを確かめてよい連携先（`introspection_clients`、空なら今までどおり）

- リソースの登録に `introspection_clients`（連携先の client_id。100 件まで）を足す（SQLite 00078、PostgreSQL 00061）。
  管理 API の作成・置き換えで受け、監査ログに載せる
- 空なら今までどおり、認証した連携先ならどれでもイントロスペクションできる。空でなければ、`aud` にそのリソースを含むトークン
  （人の認可・`sat_…`・Token Exchange で替えたもの）を、ここに載っていない連携先が確かめたときは `active: false`（理由は返さない）
- 登録の変更は、発行済みのトークンにも次のイントロスペクションから効く
- API キーは `aud` を持たないので、この限定は効かない。API キーを外のリソースサーバーに渡したくないホスト先は
  `api_key_introspection` を有効にしない

## 結果

- リソースサーバーは、人とサービスアカウントのどちらの呼び出しかと、その認証の方式を、イントロスペクションの応答だけで分けられる
- 寿命の長い API キーをリソースサーバーで受けたいホスト先は、フィーチャーを有効にすれば使える。要らないホスト先は今までどおり
  API キーが管理 API の外に出ない
- 同じ iam に複数の API（internal・partner・public など）を登録したとき、別の API のトークンを持ち込まれても、リソースサーバーの
  `aud` の確かめに加えて iam の側でも弾ける。登録しなければ今までどおり
- イントロスペクションのたびに、`aud` のリソースを 1 件引く読み出しが増える

## 検討した代替案

- **API キーを常にイントロスペクションで受ける**：使わないホスト先にも、寿命が長く向け先の無い秘密がリソースサーバーを通る経路が
  できる。既定オフのフィーチャーにする
- **API キーにも向け先（リソース）を持たせる**：認証情報の形と管理 API が変わり、移行も要る。向け先が要るなら、API キーの代わりに
  リソースに向けた `sat_…` を使えばよい
- **`aud` の確認をリソースサーバーだけに任せる（ADR 0112 のまま）**：RFC 7662 ではそれで足りるが、リソースサーバーの実装の
  誤りを iam の側で補えない。空なら今までどおりの項目にして、選べるようにする
- **呼び出し元の連携先をリソースに自動で結ぶ（resource の URI と連携先の登録を照らす）**：リソースサーバーの連携先とリソースの
  対応は 1 対 1 とは限らない（複数の構成・移行中の 2 つの連携先）。明示の一覧にする
