# 0091. 同じバイナリを役割ごとに別のプロセスで動かせるようにする

- 状態: 承認
- 日付: 2026-11-02
- 関連: [design.md](../design.md) 2.2、[0001](0001-authn-authz-monorepo.md)、[0003](0003-ports-and-adapters.md)、[0010](0010-feature-toggles.md)、
  [0083](0083-multi-realm.md)、[0089](0089-enterprise-full-scope.md)

## 背景

iam は 1 つのバイナリと 1 つのプロセスで、公開 API・管理 API・OIDC・認可の判定をすべて動かしている。モジュールの境界は
0001 で守っていて、必要になれば切り出せる形になっている。

エンタープライズの構成では、役割ごとに置き場所と規模を変えたいことが多い。OIDC だけを DMZ に置く、認可の判定だけを
横に増やす、Org の管理や認可の管理を別のチームが運用する、SCIM や管理 API は内部ネットワークだけに置く、などである。一方で、別のリポジトリ・別のバイナリのマイクロサービスにすると、
1 人での運用には重く、ホットパスに同期のネットワーク呼び出しが入る（0010 に反する）。

## 決定

- コードはモジュラーモノリスのまま、同じバイナリを役割を選んで起動できるようにする：`iam serve -roles public,oidc` のように指定する。
  指定しなければ、今までどおり全部の役割を 1 つのプロセスで動かす
- 役割は次のとおり。フィーチャーを足すときに、どの役割に属するかを決める
  - `public`：ログイン・復旧・本人の情報と認証手段、ホスト型ログイン画面、Org の切り替え
  - `oidc`：OIDC／OAuth の Provider
  - `org`：Org とその中の管理（作成・削除・設定、メンバー・招待・停止、ドメインの所有証明、Org 専用 SSO の connection、
    Org 管理ユーザー、ログインポリシー、Quota、階層）。公開 API の `/v1/me/orgs/{id}/…` のうち管理の操作と、管理 API の `/v1/admin/orgs/…`・`/v1/admin/memberships/…`
  - `authz`：認可の判定（`check`）。ほかの役割に依存せず、Storage とキャッシュだけで判定する
  - `authz-manage`：ロール・付与・Group・リスクの種類・操作の名前空間の管理（公開 API の Org の範囲と、管理 API の realm の範囲）
  - `admin`：上の役割に入らない管理 API（ユーザー、サービスアカウント、連携先、署名鍵、realm）
  - `scim`、`saml`、`worker`（予約の処理・保持期間の掃除・outbox の配信・Back-Channel Logout）
- ログインのときの Org の決定と、セッションの検証での Org・Membership の状態の確認は、`public` と `oidc` が Storage を読んで自分で行う。
  `org` の役割を同期で呼ばない
- 境界を分けるために、次のコードの依存を切る
  - `authz` はすでに `authn` を import していない（0001）。`authz/check` と `authz/manage` の間は、`manage` が `check` を使う向きだけにする
  - `authn/org` は `authn/session`・`authn/passkey`・`authn/account` を import している。Org の管理の処理が必要とするもの
    （セッションの失効、passkey の既定 Org の解除、アカウントの状態）をポートかイベント（outbox）に置き換え、`org` の役割が他の役割のパッケージを import しないようにする
- 役割の間は、Storage と EphemeralStore を共有して連携する（今の複数インスタンスと同じ）。ほかの役割の処理を同期で呼ぶ必要があるときは、
  ポートの実装を HTTP か gRPC のクライアントにしたアダプタで差し替える。同じプロセスにあれば関数呼び出しのまま
- ホットパス（セッションの検証、トークンの検証、認可の判定）は、役割をまたいでも同期のネットワーク呼び出しにしない。
  Storage とキャッシュから自分で判定する
- `worker` の処理は、`worker` の役割を持つプロセスだけが動かす。`worker` が複数あっても処理が重ならないことは、
  今の複数インスタンスでの扱いに従う。足りなければ、実装のときに Storage のロックを足す
- モジュールの境界の検査（`internal/archtest`）に、役割の間の依存の検査を足す

## 結果

- 役割ごとに置き場所・規模・公開範囲を変えられる。小さな構成は今までどおり 1 プロセスで動く
- 同じバイナリなので、ビルド・署名・台帳（0011）の仕組みは変わらない
- `authn/org` の依存を切る作業が要る。Org の管理の中でセッションを失効するような処理は、同じトランザクションでなく outbox 経由になるので、
  反映の遅れの上限（5.3）に入るかを確かめる
- 役割の組み合わせの数だけ構成が増える。CI では「全部を 1 プロセス」と「役割ごとに分けた構成」の 2 つで E2E を回す

## 検討した代替案

- 境界を守るだけで、1 プロセスのまま：置き場所と規模を役割ごとに変えられない
- 別のバイナリのマイクロサービスにし、gRPC でつなぐ：運用と遅延のコストが大きく、ホットパスに同期の呼び出しが入る
