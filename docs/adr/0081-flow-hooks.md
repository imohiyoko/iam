# 0081. フロー フックは同期の判定だけを持ち、トランザクションの中でタイムアウトを付けて呼ぶ

- 状態: 承認
- 日付: 2026-10-27
- 関連: [design.md](../design.md) 4.9、11.8、[0045](0045-internal-and-external-ids.md)、[0080](0080-custom-attributes.md)

## 背景

ホスト先は、登録の許可リスト・招待制、ログインの追加の判定、退会の一時的な保留、ID トークンへのクレームの追加を、
IAM を作り直さずに足したい。design.md 11.8 は4つの同期のフックと非同期のイベントを挙げ、「Go インターフェースか Webhook で
実装する。タイムアウト必須、失敗時の fail-closed / fail-open はフックごとに設定する。ホットパスには置かない。」とする。

## 決定

- フィーチャー `flow_hooks`（依存なし、データなし）。フックは設定の `hooks` に名前ごとに置く。`url` があれば Webhook、
  無ければ組み込む側が `app.Deps.Hooks`（`port.FlowHook`）で渡す。どちらも無ければ起動を拒否する
- フックと呼ぶ場所：
  - `pre_registration`：メールのコード・招待・外部 IdP でユーザーを作る直前。運営者が作るときは呼ばない。
    入力は `email` と `verified_via`
  - `post_authentication`：本人確認を終え、制限の無いセッションを作る直前（2要素目を待つ間は呼ばず、2要素目の後に呼ぶ）。
    入力は `user_id` と `auth_methods`
  - `pre_membership_end`：本人の離脱（`left`）と除名（`removed`）の直前。Org やアカウントの削除では呼ばない。
    止めれば 409 `membership_end_held`
  - `pre_token`：ID トークンを作る直前（コードの交換とリフレッシュ）。入力は `user_id`（`sub`）・`client_id`・`scopes`・
    `auth_methods`・`org_id`。`claims` を返せば ID トークンに足す。IAM が決めるクレーム（`iss`・`sub`・`aud`・`exp`・
    `org_id`・`email`・`attributes` など）は足せず、20 個・4096 バイトまで。規則に合わなければトークンを発行しない（500）。
    止めれば `invalid_grant`
- 止めたとき（`allow: false`）は、本人確認の後の拒否として 403 と理由のコード `hook_denied.<hook>` を返す（4.9）。
  フックの `reason` は IAM のログにだけ残し、利用者には返さない
- タイムアウトは既定 2 秒、上限 5 秒。失敗（タイムアウト・200 以外・誤った JSON・64 KiB を超える応答）は、既定で止める
  （fail-closed）。`fail_open: true` なら通す。期限を過ぎて返った結果は使わない。呼び出し元の取り消しは失敗として扱わない
- Webhook：HookInput の JSON を POST し、`X-IAM-Signature: t=<UNIX 秒>,v1=<hex(HMAC-SHA-256(secret, "<t>." + body))>`
  （通知の Webhook と同じ形）と `X-IAM-Hook` を付ける。宛先は https（`dev: true` のときだけ http）、転送には従わない。
  秘密は `secret_env` の環境変数（32 バイト以上）から読み、読んだ後に消す
- 入力の ID は公開 ID だけ（0045）。realm は slug で渡す
- フックは呼ぶ操作のトランザクションの中で呼ぶ（止めれば何も書かない）。そのためタイムアウトの上限を短くする
- 非同期のイベントは新しく作らず、既存の EventSink（outbox）で受け取る

## 理由

- 判定を返すだけの同期のフックに絞れば、失敗の扱い（fail-closed / open）とタイムアウトだけで振る舞いが決まる
- トランザクションの中で呼べば、止めたときに途中まで書いた状態が残らない。代わりに、遅いフックは接続を握るので上限を短くする
- セッションの検証・認可の判定・イントロスペクションでは呼ばない（ホットパスの遅れと可用性をフックに預けない）
- クレームの上書きを許すと、連携先が IAM の決めた値（`sub`・`org_id`）を信じられなくなる

## 影響

- フックの遅れはログイン・登録・トークンの発行の遅れになる。fail-closed のフックが落ちれば、その操作は止まる
- 受け取る側は署名と時刻のずれ（5 分など）を確かめる
- アクセストークンは不透明なので、クレームは ID トークンにだけ足す（UserInfo・イントロスペクションには足さない）

## 検討した代替案

- トランザクションの外で呼ぶ：止めたときの取り消しが要り、止めた後に書いた状態が見えうる
- フックがユーザーの値を書き換える（作るユーザーの属性など）：失敗時の扱いが複雑になる。属性は管理 API（0080）で書く
- 非同期のフックを別に作る：EventSink と同じものが2つになる
