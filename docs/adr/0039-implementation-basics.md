# 0039. 実装の基本（HTTP、SQL、マイグレーション、ID、M1 のログイン方法）

- 状態: 承認
- 日付: 2026-10-25
- 関連: [design.md](../design.md) 2.4, 7

## 背景

M0 のコードを書き始める前に、後から変えると手戻りが大きい実装の基本を決める必要がある。

## 決定

- **HTTP**：標準の `net/http` を使う。API は OpenAPI で定義し（2.5）、oapi-codegen でサーバー側の型とハンドラの枠を生成する
- **SQL**：sqlc を使う。SQL を書くと、型付きの Go コードが生成される。Storage アダプタごとに、その DB に最適な SQL を書く（0004）
- **マイグレーション**：goose を使う。Storage アダプタごとに持つ
- **ID**（[0045](0045-internal-and-external-ids.md) で、内部 ID と外部 ID に分けた）：UUIDv7 に型付きの接頭辞を付ける（`usr_01J...`、`org_01J...`）。UUIDv7 は生成時刻の順に並ぶため、DB のインデックスの効率が良い。接頭辞で ID の取り違えを防ぐ。DB での保存形式はアダプタが決める
- **M1 のログイン方法**：マジックリンク / メールコードと OAuth 1種。パスワード、passkey、TOTP は M2

## 結果

- フレームワークへの依存が少なく、標準ライブラリの範囲で読める
- OpenAPI の定義が API の契約の正になり、SDK の生成にも使える（11.10）
- sqlc は PostgreSQL・MySQL・SQLite に対応しており、アダプタごとの最適化（0004）と相性が良い

## 検討した代替案

- Web フレームワーク（Echo、Gin など）：標準の `net/http` のルーティングで足りるため不要
- ORM（GORM など）：DB ごとの最適化がしにくく、生成される SQL が見えにくい
- ULID：UUIDv7 と性質は近いが、UUID 型を持つ DB でそのまま扱える UUIDv7 を選ぶ
